# AI 개발 및 프론트엔드 인수인계 가이드

이 문서는 기획자가 AI에게 웹 프론트엔드 구현을 요청할 때 사용하는 공통 개발 지침이다.

목표는 빠르게 보이는 화면만 만드는 것이 아니라, 이후 프론트엔드 개발자가 구조를 이해하고 안전하게 수정·확장할 수 있는 코드를 만드는 것이다. AI는 작업을 시작하기 전에 이 문서를 끝까지 읽고, 저장소에 더 구체적인 작업 규칙이 있으면 함께 따라야 한다.

---

## 1. AI에게 전달할 기본 명령

기획자는 기능 요청과 함께 아래 내용을 AI에게 전달한다.

```text
작업을 시작하기 전에 이 저장소의 작업 규칙과
docs/ai-development-handoff-guidelines.md를 전부 읽어 주세요.

현재 프로젝트의 구조와 기존 구현 방식을 먼저 분석하고,
프론트엔드 개발자가 이어서 유지보수하기 쉬운 형태로 구현하세요.

특정 라이브러리를 임의로 추가하거나 기존 구조를 새 방식으로 교체하지 마세요.
새로운 기술 결정이 필요하면 구현 전에 선택지, 이유, 영향 범위를 알려 주세요.

구현 후 변경 파일, 주요 설계 판단, 실행 방법, 테스트 결과,
남은 작업과 주의사항을 정리해 주세요.
```

기능 요구사항은 다음 형식을 권장한다.

```text
[목적]
누가 어떤 문제를 해결하기 위해 사용하는 기능인지 설명

[사용자 흐름]
사용자가 진입해서 작업을 완료하기까지의 순서

[화면 및 상태]
기본, 로딩, 빈 상태, 오류, 성공, 권한 없음 상태

[업무 규칙]
필수 입력, 제한 조건, 노출 조건, 권한, 예외 상황

[완료 조건]
사용자가 실제로 무엇을 할 수 있어야 완료인지 설명

[참고 자료]
디자인, 기존 화면, 정책 문서, API 문서 링크
```

## 2. 구현 전 확인 사항

AI는 코드를 수정하기 전에 다음을 확인한다.

1. 저장소의 작업 규칙 문서를 읽는다.
2. 현재 폴더 구조와 각 영역의 책임을 파악한다.
3. 기존에 비슷한 화면, 컴포넌트, 데이터 처리 방식이 있는지 찾는다.
4. 현재 사용 중인 실행, 검사, 테스트, 빌드 명령을 확인한다.
5. 수정 대상과 관련 없는 사용자 변경 사항이 있는지 확인하고 보존한다.
6. 요구사항에서 빠진 로딩, 빈 상태, 오류, 권한, 모바일 상태를 식별한다.
7. 구현을 위해 새로운 기술 결정이 필요한지 판단한다.

기존 코드에서 해결 방법을 찾을 수 있으면 기존 방식을 우선 사용한다. 단순히 더 익숙하거나 최신이라는 이유로 구조, 상태 관리 방식, 스타일 체계 또는 빌드 방식을 교체하지 않는다.

## 3. 프로젝트 구조 원칙

폴더 이름은 프로젝트의 기존 규칙을 따르되, 책임은 다음과 같이 분리한다.

```text
src/
├─ app/          앱 초기화, 전역 설정, 라우팅, 전역 오류 처리
├─ pages/        URL로 접근하는 화면과 화면 조합
├─ widgets/      여러 기능과 컴포넌트를 조합한 큰 화면 영역
├─ features/     사용자의 행동과 업무 기능
├─ entities/     핵심 도메인 데이터와 관련 로직
├─ shared/       여러 도메인에서 재사용하는 기반 코드
└─ fixtures/     개발·퍼블리싱·테스트용 예시 데이터
```

프로젝트가 다른 구조를 이미 사용한다면 위 구조로 강제 변경하지 않는다. 대신 다음 책임 원칙을 지킨다.

- 페이지는 화면을 조합하고 라우트 입력을 해석한다.
- 업무 규칙은 화면 JSX나 스타일 파일에 숨기지 않는다.
- 데이터 접근 코드는 표현 컴포넌트와 분리한다.
- 공통 컴포넌트는 특정 페이지의 업무 내용을 알지 못해야 한다.
- 특정 기능에서만 쓰는 코드를 성급하게 공통 영역으로 이동하지 않는다.
- 서로 다른 도메인의 내부 구현을 직접 참조하지 않는다.
- 상위 영역은 하위 기반 영역을 사용할 수 있지만 하위 영역이 특정 페이지를 참조하지 않도록 한다.

파일은 단순히 줄 수가 많다는 이유로 나누지 않는다. 서로 다른 책임, 변경 이유 또는 테스트 경계를 가질 때 분리한다.

### 신규 웹 프로젝트 기본 기술

기존 기술 제약이 없는 신규 웹 프론트엔드 프로젝트는 React와 TypeScript 조합을 기본으로 한다. TypeScript의 엄격한 타입 검사를 활성화하고 타입 오류를 우회하지 않는다.

기존 프로젝트가 다른 기술로 운영 중이거나 고객사·플랫폼 제약이 있으면 현재 기술을 존중한다. 기존 프로젝트를 React로 전환하는 작업은 별도의 마이그레이션 합의 없이 수행하지 않는다.

## 4. 컴포넌트 설계 원칙

컴포넌트는 역할과 입력이 명확해야 한다.

- 컴포넌트 이름은 화면에서 맡는 역할을 나타낸다.
- 외부 데이터 출처를 직접 알 필요가 없는 컴포넌트는 props로 데이터를 받는다.
- 표시, 데이터 조회, 폼 처리, 업무 판단을 하나의 큰 컴포넌트에 모두 넣지 않는다.
- 같은 마크업이 두 번 보인다는 이유만으로 즉시 공통 컴포넌트화하지 않는다.
- 의미와 동작이 같은 UI가 반복될 때 공통화를 검토한다.
- boolean props가 계속 늘어나 서로 다른 화면을 하나의 컴포넌트로 억지로 처리하지 않는다.
- 숨겨진 전역 값이나 브라우저 저장소에 의존하기보다 입력과 출력이 드러나게 만든다.
- 버튼, 링크, 입력, 제목 등은 올바른 HTML 의미 구조를 사용한다.

한 파일을 수정할 때 다른 화면이 예상치 않게 바뀌지 않도록 페이지 전용 스타일과 공통 스타일의 범위를 명확히 한다.

---

## 5. 상태 관리 원칙

상태는 필요한 가장 가까운 위치에 둔다.

- 입력 중인 값, 모달 열림, 탭 선택 등 일시적인 상태는 해당 화면이나 기능에서 관리한다.
- 서버에서 가져온 데이터를 별도 전역 상태에 중복 저장하지 않는다.
- 새로고침 후 복원하거나 링크로 전달해야 하는 상태는 URL 표현을 우선 검토한다.
- 여러 화면에서 공유한다는 이유만으로 모든 상태를 전역화하지 않는다.
- 계산 가능한 값은 별도 상태로 저장하지 않고 원본 상태에서 계산한다.
- 인증과 권한은 클라이언트 저장값만으로 확정하지 않는다.
- 상태의 소유자와 변경 경로가 한눈에 드러나게 한다.

새로운 전역 상태가 필요하면 다음 내용을 먼저 기록한다.

- 어떤 화면들이 공유하는가
- URL이나 서버 데이터로 해결할 수 없는 이유는 무엇인가
- 상태가 언제 생성되고 폐기되는가
- 새로고침 시 유지되어야 하는가

---

## 6. 데이터 및 API 경계

화면이 데이터 통신 세부사항에 직접 의존하지 않게 한다.

- API 주소와 요청 형식을 페이지 곳곳에 직접 작성하지 않는다.
- 요청, 응답 변환, 오류 해석은 프로젝트의 데이터 접근 계층을 통과한다.
- 서버 응답 타입과 화면 표시용 모델이 다르면 변환 경계를 명확히 한다.
- 화면 컴포넌트가 서버의 불필요한 필드 구조까지 알지 않게 한다.
- 로딩, 빈 데이터, 오류, 재시도 상태를 명시적으로 처리한다.
- 오류를 무조건 성공처럼 처리하거나 임시 데이터로 조용히 대체하지 않는다.
- fixture를 실제 운영 데이터나 인증 근거로 사용하지 않는다.
- 개발용 fixture는 실제 데이터로 교체하기 쉬운 입력 형태로 분리한다.
- 날짜, 금액, 단위, 시간대와 다국어 표시는 한 곳에서 일관되게 처리한다.

API가 확정되지 않은 퍼블리싱 단계에서는 실제 통신을 추측해 만들지 않는다. 화면에 필요한 fixture와 컴포넌트 입력 계약을 먼저 정의하고, 미확정 항목을 문서에 남긴다.

---

## 7. 폼과 사용자 입력

모든 폼은 정상 입력만이 아니라 실패 상황까지 설계한다.

- label과 입력 요소의 관계를 명확히 한다.
- 필수값, 길이, 형식, 범위와 상호 의존 조건을 정의한다.
- 검증 메시지는 사용자가 수정 방법을 이해할 수 있게 작성한다.
- 제출 중 중복 요청을 방지한다.
- 서버 오류와 입력 검증 오류를 구분한다.
- 저장 성공, 실패, 취소와 이탈 시 동작을 정의한다.
- 사용자가 작성한 내용이 예기치 않게 사라지지 않도록 한다.
- 키보드만으로도 입력과 제출이 가능해야 한다.

기획 요구사항에 검증 규칙이 없다면 AI가 업무 규칙을 임의로 확정하지 않는다. 일반적인 안전 검증만 적용하고, 정책 결정이 필요한 항목은 남은 작업으로 기록한다.

## 8. UI, 반응형 및 접근성

기존 디자인 시스템과 화면 패턴을 우선 사용한다.

- 색상, 글꼴, 간격, 반경과 그림자는 토큰 또는 기존 공통 값을 사용한다.
- 페이지마다 비슷한 값을 새로 만들지 않는다.
- 데스크톱뿐 아니라 프로젝트가 지원하는 최소 모바일 너비를 확인한다.
- 긴 텍스트, 빈 값, 많은 항목과 작은 화면에서도 잘림과 가로 스크롤이 없어야 한다.
- 클릭 가능한 요소는 충분한 조작 영역을 갖는다.
- 색상만으로 상태를 구분하지 않는다.
- 이미지에는 목적에 맞는 대체 텍스트를 제공한다.
- 제목 순서, landmark, label, focus와 키보드 이동을 확인한다.
- 모달이 열리면 초점 이동, 닫기, 배경 상호작용을 올바르게 처리한다.
- 로딩 중 화면 흔들림과 중복 클릭을 줄인다.
- 인쇄 화면에서는 앱 내비게이션과 불필요한 조작 요소를 숨긴다.

디자인 원본이 있는 작업에서는 AI가 임의로 개선하거나 현대화하지 않는다. 차이가 필요하면 적용 전에 이유와 영향을 설명하고 승인을 받는다.

### 퍼블리싱은 필요한 만큼만 구현한다

- 기획에 없는 화면 단계, 탭, 모달, URL과 설정을 추가하지 않는다.
- 한 화면의 단순 상태를 위해 전역 상태나 복잡한 데이터 구조를 만들지 않는다.
- 재사용 가능성이 불확실한 UI를 미리 범용 컴포넌트로 만들지 않는다.
- 한 번만 사용하는 작은 요소를 과도하게 많은 파일로 나누지 않는다.
- CSS와 의미 있는 HTML로 해결할 수 있는 표현을 JavaScript로 재구현하지 않는다.
- 퍼블리싱 단계에서 미확정 API, 인증과 서버 구조를 추측해 만들지 않는다.
- 미래의 가능성보다 현재 요구사항의 명확성, 읽기 쉬운 데이터 흐름과 수정 용이성을 우선한다.

복잡한 구조가 실제 요구사항 때문에 필요하다면 단순 구현으로 해결할 수 없는 이유와 유지보수 영향을 먼저 설명한다.

## 9. 라이브러리 및 기술 선택 원칙

이 문서는 특정 라이브러리를 강제하지 않는다. 프로젝트가 이미 채택한 도구와 패턴을 우선한다.

새로운 라이브러리는 다음 조건을 모두 검토한 뒤에만 도입한다.

1. 기존 코드나 플랫폼 기본 기능만으로 해결하기 어려운가
2. 추가되는 기능에 비해 번들, 학습, 보안과 유지보수 비용이 적절한가
3. 프로젝트의 현재 기술 방향과 충돌하지 않는가
4. 라이선스와 장기 유지 가능성을 확인했는가
5. 제거하거나 교체해야 할 때 영향 범위가 명확한가

AI는 사용자 승인 없이 새로운 라이브러리를 설치하지 않는다. 필요할 경우 다음 형식으로 제안한다.

```text
[해결하려는 문제]
[기존 방식으로 어려운 이유]
[도입 선택지]
[각 선택지의 장단점]
[추천안과 영향 범위]
```

기술 선택이 확정되면 선택 이유와 영향을 별도 결정 기록에 남긴다. 버전 번호는 실제 설정 파일에서 관리하고, 이 지침 문서에 고정하지 않는다.

## 10. 테스트 및 검증 기준

구현 완료는 화면이 한 번 표시되는 상태를 의미하지 않는다.

변경 범위에 맞게 다음을 검증한다.

- 정적 검사와 타입 검사
- 핵심 업무 규칙 단위 테스트
- 사용자 입력과 화면 상태 테스트
- API 성공, 실패와 빈 응답 테스트
- 주요 사용자 흐름 통합 또는 E2E 테스트
- 지원하는 데스크톱·모바일 화면 확인
- 키보드 탐색과 기본 접근성 확인
- production build 확인

모든 세부 구현에 동일한 양의 테스트를 강제하지 않는다. 다만 다음 영역은 우선적으로 테스트한다.

- 금액, 권한, 인증, 개인정보와 관련된 로직
- 여러 조건에 따라 결과가 달라지는 업무 규칙
- 사용자 입력을 저장하거나 삭제하는 동작
- 장애가 발생했을 때 복구가 어려운 흐름
- 과거에 오류가 발생한 기능

테스트가 실행되지 못했다면 통과했다고 표현하지 않고, 실행하지 못한 이유와 필요한 후속 조치를 기록한다.

---

## 11. 보안과 개인정보

- 비밀번호, 인증 토큰, API 키와 개인정보를 코드나 fixture에 실제 값으로 저장하지 않는다.
- 브라우저 저장소를 권한 검증의 최종 근거로 사용하지 않는다.
- 사용자 입력을 신뢰하지 않고 출력 위치와 전송 목적에 맞게 처리한다.
- 오류 화면이나 로그에 민감정보를 노출하지 않는다.
- 외부 링크, 파일 업로드와 다운로드는 허용 형식과 실패 상황을 고려한다.
- 개인정보가 포함된 예시는 명백한 가상 데이터로 작성한다.
- 분석, 모니터링 또는 외부 서비스로 데이터를 보내야 하면 전송 범위와 동의를 확인한다.

보안 정책이 확정되지 않은 경우 AI가 임의로 약한 대안을 구현하지 않고 의사결정 필요 사항으로 남긴다.

---

## 12. 주석과 문서화

코드가 무엇을 하는지 그대로 반복하는 주석은 작성하지 않는다. 다음 내용을 중심으로 기록한다.

- 일반적이지 않은 업무 규칙의 이유
- 외부 시스템 제약 때문에 선택한 구현
- 제거 조건이 명확한 임시 처리
- 잘못 수정하기 쉬운 경계와 전제조건

기능을 추가하거나 구조를 변경했다면 관련 문서도 함께 갱신한다.

- 실행 방법이 바뀌면 프로젝트 안내 문서 갱신
- 환경 설정이 추가되면 예시 환경 파일과 설명 갱신
- 새로운 구조나 의존 방향이 생기면 아키텍처 문서 갱신
- 새로운 기술 결정을 했다면 결정 기록 추가
- 완료 또는 남은 기능이 바뀌면 체크리스트 갱신

---

## 13. 금지 사항

AI는 명시적인 요청 없이 다음 작업을 하지 않는다.

- 프로젝트 전체 구조를 한 번에 재편한다.
- 기존 구현 방식을 새 유행이나 개인 선호로 교체한다.
- 비슷한 목적의 라이브러리를 중복 도입한다.
- 페이지 내부에 대량의 fixture 또는 업무 데이터를 직접 작성한다.
- 타입 오류를 강제 형변환이나 검사 비활성화로 숨긴다.
- 실패한 요청을 성공으로 표시한다.
- 접근 권한을 클라이언트 화면 숨김만으로 처리한다.
- 사용자 데이터를 브라우저 저장소에 무분별하게 보관한다.
- 테스트를 삭제하거나 느슨하게 바꿔 변경 사항을 통과시킨다.
- 관련 없는 코드를 함께 정리하거나 포맷한다.
- 사용자 변경 사항을 되돌린다.
- 실행하지 않은 검증을 완료했다고 보고한다.
- 요구사항에 없는 디자인, 기능 또는 업무 정책을 임의로 추가한다.
- 퍼블리싱 화면을 불필요한 추상화, 전역 상태와 과도한 컴포넌트 분리로 복잡하게 만든다.

---

## 14. 완료 조건

다음 조건을 만족해야 기능 구현을 완료로 보고할 수 있다.

- 요구된 사용자 흐름이 실제로 동작한다.
- 기본, 로딩, 빈 상태, 오류와 성공 상태가 처리된다.
- URL 직접 접근과 새로고침이 필요한 화면은 상태를 복원한다.
- 기존 프로젝트 구조와 의존 방향을 지킨다.
- 요구사항에 비해 불필요한 구조, 상태와 추상화가 없다.
- fixture, API, 업무 로직과 UI 책임이 구분된다.
- 데스크톱과 지원 모바일 너비에서 확인했다.
- 키보드 조작과 기본 접근성 요구를 확인했다.
- 정적 검사, 테스트와 production build 결과를 확인했다.
- 임시 처리와 미확정 정책이 문서에 남아 있다.
- 관련 체크리스트와 개발 문서가 갱신됐다.
- 비교용 파일, 디버그 코드와 불필요한 로그가 남아 있지 않다.

일부 조건을 확인하지 못했다면 구현 완료와 검증 완료를 구분해 보고한다.

---

## 15. 프론트엔드 개발자에게 남길 인수인계 형식

AI는 작업 종료 시 다음 형식으로 결과를 남긴다.

```md
## 구현 결과
- 사용자가 할 수 있게 된 일

## 주요 변경 파일
- 파일 경로: 담당 역할

## 설계 판단
- 선택한 구조와 이유
- 기존 패턴을 재사용한 부분

## 데이터 및 API
- 사용한 fixture 또는 API
- 미확정 계약과 교체 지점

## 검증 결과
- 실행한 명령과 결과
- 확인한 화면 크기와 사용자 흐름

## 남은 작업
- 미구현 기능
- 정책 또는 디자인 결정 필요 사항
- 알려진 제한 사항

## 주의사항
- 다음 개발자가 수정할 때 확인해야 할 경계
```

“구현 완료”만 남기지 말고, 다음 개발자가 코드를 다시 조사하지 않아도 변경 목적과 검증 범위를 파악할 수 있게 작성한다.

---

## 16. 기획자가 확인할 최종 체크리스트

기획자는 AI 결과를 받을 때 다음을 확인한다.

- [ ] 요구한 사용자 흐름이 모두 구현됐는가
- [ ] 로딩, 빈 상태와 오류 화면이 있는가
- [ ] 모바일에서도 사용할 수 있는가
- [ ] 임의로 추가된 기능이나 디자인이 없는가
- [ ] 실제 데이터와 예시 데이터가 구분돼 있는가
- [ ] 새 라이브러리나 구조 변경이 사전 합의 없이 들어가지 않았는가
- [ ] 테스트와 빌드 결과가 구체적으로 기록됐는가
- [ ] 미구현 항목과 정책 결정 사항이 숨겨지지 않았는가
- [ ] 변경 파일과 실행 방법이 정리돼 있는가
- [ ] 프론트엔드 개발자가 이어받을 인수인계 내용이 있는가

이 체크리스트에서 확인되지 않은 항목은 AI에게 근거 또는 추가 검증을 요청한다.
