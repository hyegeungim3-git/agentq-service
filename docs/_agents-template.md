# 프로젝트 AI 작업 규칙 템플릿

> 이 파일은 여러 웹 프론트엔드 프로젝트에서 복사해 사용할 수 있는 범용 템플릿이다.
>
> 프로젝트를 시작할 때 파일명을 `AGENTS.md`로 변경하고, `[작성 필요]` 또는 대괄호로 표시된 내용을 실제 프로젝트 정보로 교체한다. 작성이 끝난 안내 문구와 불필요한 예시는 삭제한다.

## 1. 문서 적용 우선순위

AI는 작업을 시작하기 전에 다음 문서를 순서대로 확인한다.

1. 이 `AGENTS.md`
2. `[AI 개발 및 프론트엔드 인수인계 가이드 경로]`
3. 기능별 기획 문서
4. 디자인 또는 화면 명세
5. API 계약과 데이터 명세
6. 테스트 및 배포 문서

문서가 충돌하면 더 구체적이고 현재 작업에 가까운 프로젝트 문서를 우선한다. 우선순위를 판단하기 어렵거나 결과가 크게 달라질 수 있으면 임의로 결정하지 말고 사용자에게 알려야 한다.

### 핵심 사용자 가치

`[사용자가 이 제품을 통해 얻어야 하는 핵심 가치 작성]`

`[현재 릴리스 또는 개발 단계에서 달성할 구체적인 목표 작성]`

## 3. 필수 참고 자료

- 제품 요구사항: `[경로 또는 링크]`
- 디자인 기준: `[경로 또는 링크]`
- 화면 및 URL 목록: `[경로 또는 링크]`
- API 문서: `[경로 또는 링크, 미확정이면 미확정이라고 작성]`
- 데이터 정책: `[경로 또는 링크]`
- 테스트 기준: `[경로 또는 링크]`
- 배포 문서: `[경로 또는 링크]`

참고 자료가 없거나 접근할 수 없으면 AI가 내용을 추측해 확정하지 않는다. 구현 가능한 범위와 결정이 필요한 범위를 구분해 보고한다.

## 4. 작업 시작 전 필수 절차

AI는 코드를 수정하기 전에 다음을 수행한다.

1. 관련 작업 규칙과 기획 문서를 끝까지 읽는다.
2. 저장소 구조와 기존 구현 패턴을 확인한다.
3. 비슷한 화면, 기능, 컴포넌트와 데이터 처리 코드가 있는지 찾는다.
4. 현재 변경 사항을 확인하고 사용자 작업을 보존한다.
5. 요구사항과 기존 코드 또는 문서의 충돌 여부를 확인한다.
6. 구현 범위, 검증 방법과 예상 변경 파일을 정리한다.
7. 새로운 기술 결정이나 권한이 필요한 작업은 구현 전에 알린다.

기존 구현으로 해결할 수 있는 문제에 새로운 구조나 기술을 임의로 도입하지 않는다.

## 5. 프로젝트 구조

현재 프로젝트의 실제 구조를 아래에 기록한다.

```text
[프로젝트 루트]/
├─ [앱 초기화 및 전역 설정 영역]
├─ [페이지 또는 라우트 영역]
├─ [업무 기능 영역]
├─ [도메인 데이터 영역]
├─ [공통 코드 영역]
├─ [정적 자산 영역]
├─ [테스트 영역]
└─ [문서 영역]
```

### 영역별 책임

| 영역 | 책임 | 참조 가능 범위 |
|---|---|---|
| `[영역명]` | `[담당 역할]` | `[참조 가능한 영역]` |
| `[영역명]` | `[담당 역할]` | `[참조 가능한 영역]` |
| `[영역명]` | `[담당 역할]` | `[참조 가능한 영역]` |

프로젝트에 이미 구조가 있으면 범용 예시 구조로 강제 변경하지 않는다. 기존 구조 안에서 책임과 의존성 경계를 유지한다.

## 6. 구현 원칙

### 책임 분리

- 페이지는 라우트 입력을 해석하고 화면을 조합한다.
- 데이터 접근, 업무 규칙과 화면 표현을 구분한다.
- 공통 UI는 특정 페이지나 업무 도메인의 세부사항을 알지 않게 한다.
- 특정 기능에서만 사용하는 코드는 성급하게 공통 영역으로 이동하지 않는다.
- 서로 다른 변경 이유를 가진 코드는 책임에 따라 분리한다.
- 계산 가능한 값을 불필요하게 별도 상태로 저장하지 않는다.

### 기존 코드 존중

- 기존 명명, 폴더, 스타일과 테스트 방식을 우선 사용한다.
- 관련 없는 코드를 함께 리팩터링하거나 포맷하지 않는다.
- 사용자 또는 다른 개발자의 변경 사항을 되돌리지 않는다.
- 새 기능 때문에 프로젝트 전체 구조를 한 번에 변경하지 않는다.
- 기존 공개 동작을 변경해야 한다면 영향 범위를 먼저 설명한다.

### 유지보수성

- 이름만으로 역할을 이해할 수 있게 작성한다.
- 숨겨진 전역 값보다 명시적인 입력과 출력을 사용한다.
- 임시 처리는 이유, 제거 조건과 후속 작업을 기록한다.
- 중복 제거보다 책임과 의미의 일관성을 우선한다.
- 복잡한 업무 규칙은 화면 코드에 흩어놓지 않는다.
- 다음 개발자가 변경 지점을 찾을 수 있도록 경계를 명확히 한다.

## 7. 기술 및 라이브러리 선택

### 신규 웹 프론트엔드 기본 조합

별도 기술 제약이 없는 신규 웹 프론트엔드 프로젝트는 다음 조합을 기본으로 한다.

- UI 구현: React
- 언어: TypeScript
- TypeScript의 엄격한 타입 검사를 활성화한다.
- JavaScript만으로 구현하거나 타입 검사를 우회하지 않는다.
- 컴포넌트는 함수형으로 작성하고 React의 일반적인 데이터 흐름을 따른다.

다음에 해당하면 React와 TypeScript를 무조건 강제하지 않는다.

- 이미 다른 프레임워크와 언어로 운영 중인 기존 프로젝트
- 고객사, 배포 환경 또는 플랫폼에서 기술을 지정한 프로젝트
- 정적 HTML 한 파일처럼 React 도입이 명백히 과한 단발성 결과물
- React를 사용할 수 없는 기술적 제약이 확인된 경우

예외를 적용할 때는 AI가 임의로 다른 기술을 선택하지 않고 이유와 유지보수 영향을 먼저 설명한다. 기존 프로젝트를 React로 전환하는 작업은 별도의 마이그레이션 요청이 있을 때만 수행한다.

### 추가 라이브러리 선택

React와 TypeScript 이외의 특정 라이브러리는 이 문서에서 강제하지 않는다. 저장소에 이미 도입된 기술과 패턴을 우선 사용한다.

AI는 명시적인 승인 없이 다음 작업을 하지 않는다.

- 새로운 라이브러리 설치
- 기존 핵심 라이브러리 교체
- 상태 관리, 스타일, 라우팅 또는 데이터 접근 체계 변경
- 빌드, 배포 또는 테스트 도구 교체
- 비슷한 목적의 도구 중복 도입

새로운 기술이 필요하면 다음 내용을 먼저 제시한다.

```text
[해결하려는 문제]
[현재 방식으로 해결하기 어려운 이유]
[가능한 선택지]
[각 선택지의 장단점과 유지보수 영향]
[추천안]
[변경 파일과 마이그레이션 범위]
```

확정된 기술 결정은 `[기술 결정 기록 경로]`에 이유와 영향 범위를 기록한다.

## 8. 퍼블리싱 단순성 원칙

퍼블리싱 작업의 목표는 요구된 화면과 상호작용을 정확하고 단순하게 구현하는 것이다. AI는 유지보수를 어렵게 만드는 과도한 설계나 추상화를 추가하지 않는다.

### 기본 원칙

- 원본 화면보다 정보 구조와 사용자 흐름을 복잡하게 만들지 않는다.
- 기획에 없는 단계, 탭, 모달, 설정, 애니메이션과 장식을 추가하지 않는다.
- 독립 화면이 아닌 탭, 아코디언, 모달과 폼 단계마다 URL을 만들지 않는다.
- 단순 표시 상태에 전역 상태, 복잡한 상태 머신 또는 별도 데이터 계층을 도입하지 않는다.
- 한 화면에서만 사용하는 작은 UI를 지나치게 많은 파일과 컴포넌트로 분해하지 않는다.
- 재사용 가능성이 불명확한 코드를 미리 범용화하지 않는다.
- 단순한 조건 표시를 설정 객체, 플러그인 구조 또는 동적 렌더러로 과도하게 일반화하지 않는다.
- CSS로 해결 가능한 표현을 JavaScript 계산과 런타임 측정으로 구현하지 않는다.
- 브라우저 기본 동작과 의미 있는 HTML로 해결 가능한 기능을 불필요하게 재구현하지 않는다.
- 퍼블리싱 단계에서 확정되지 않은 백엔드 구조와 API를 추측해 만들지 않는다.
- 화면 확인용 데이터는 실제 데이터 연결부와 분리된 fixture로 관리한다.
- 사용자가 보지 못하는 확장 가능성을 이유로 현재 요구사항보다 큰 시스템을 만들지 않는다.

### 컴포넌트 분리 판단

다음 중 하나에 해당할 때 컴포넌트 분리를 검토한다.

- 여러 위치에서 의미와 동작이 동일하게 반복된다.
- 독립적인 상태나 사용자 상호작용을 가진다.
- 별도의 테스트 경계가 필요하다.
- 부모 화면과 다른 이유로 변경될 가능성이 높다.
- 분리했을 때 이름과 책임이 더 명확해진다.

단순히 JSX가 길거나 두 번 등장한다는 이유만으로 즉시 공통화하지 않는다. 작은 컴포넌트가 지나치게 많아 데이터 흐름을 따라가기 어려워진다면 화면 가까이에 합쳐 두는 편을 우선한다.

### 복잡성이 필요한 경우

권한, 결제, 대규모 데이터, 실시간 동기화, 복잡한 폼 또는 명확한 확장 요구 때문에 구조가 복잡해져야 한다면 다음을 먼저 설명한다.

```text
[복잡성이 필요한 요구사항]
[단순한 구현으로 해결할 수 없는 이유]
[추가되는 구조]
[유지보수 비용과 영향 범위]
```

승인 없이 미래 요구사항을 가정해 복잡성을 추가하지 않는다.

## 9. 상태 및 데이터 관리

- 상태는 필요한 가장 가까운 위치에서 관리한다.
- 서버 데이터와 화면 임시 상태를 구분한다.
- 서버 데이터를 별도 전역 상태에 불필요하게 복제하지 않는다.
- URL로 복원하거나 공유해야 하는 상태는 URL 표현을 우선 검토한다.
- 여러 화면에서 사용한다는 이유만으로 모든 상태를 전역화하지 않는다.
- 인증과 권한은 클라이언트 값만으로 확정하지 않는다.
- 데이터의 생성, 조회, 수정과 폐기 경로를 명확하게 유지한다.

### API 경계

- 페이지에서 API 주소와 요청 세부사항을 직접 반복하지 않는다.
- 프로젝트의 공통 데이터 접근 경계를 사용한다.
- 서버 응답과 화면 모델이 다르면 변환 위치를 명확히 한다.
- 로딩, 빈 응답, 오류와 재시도 상태를 처리한다.
- 실패한 요청을 성공으로 표시하거나 조용히 임시 데이터로 대체하지 않는다.
- API가 미확정이면 임의의 운영 계약을 만들지 않고 fixture와 입력 계약을 분리한다.

### Fixture 및 예시 데이터

- 예시 데이터는 실제 운영 데이터와 명확히 구분한다.
- 대량의 예시 데이터를 화면 컴포넌트 안에 직접 작성하지 않는다.
- fixture를 실제 인증 또는 권한의 근거로 사용하지 않는다.
- 개인정보는 명백한 가상 값만 사용한다.
- 실제 API로 교체하기 쉬운 데이터 형태를 유지한다.

## 10. 화면 및 사용자 경험

각 독립 화면은 필요한 경우 다음 상태를 포함한다.

- 기본 상태
- 로딩 상태
- 빈 상태
- 오류 및 재시도 상태
- 성공 또는 완료 상태
- 권한 없음 상태
- 비활성 상태
- 긴 텍스트와 많은 데이터 상태
- 최소 지원 모바일 너비 상태

### UI 원칙

- 기존 디자인 시스템과 공통 컴포넌트를 우선 사용한다.
- 색상, 글꼴, 간격, 반경과 그림자를 임의로 반복 생성하지 않는다.
- 요구사항에 없는 디자인 개선이나 장식을 추가하지 않는다.
- 같은 화면의 섹션 순서, 문구와 정보 구조를 임의로 바꾸지 않는다.
- 데스크톱과 지원 모바일 환경에서 잘림과 가로 스크롤을 확인한다.
- 인쇄 화면이 있으면 내비게이션과 조작 요소를 출력에서 제외한다.

### 접근성 원칙

- 의미에 맞는 HTML 요소를 사용한다.
- 입력 요소에 연결된 label을 제공한다.
- 제목의 계층과 페이지 landmark를 유지한다.
- 키보드만으로 주요 기능을 사용할 수 있어야 한다.
- focus 상태가 보이고 모달의 초점 이동과 닫기가 동작해야 한다.
- 이미지에는 목적에 맞는 대체 텍스트를 제공한다.
- 색상만으로 상태를 전달하지 않는다.
- 클릭 요소는 충분한 조작 영역을 가진다.

## 11. 폼 및 사용자 입력

- 필수값, 길이, 형식, 범위와 필드 간 조건을 명확히 처리한다.
- 검증 메시지는 사용자가 수정 방법을 이해할 수 있게 작성한다.
- 입력 검증 오류와 서버 오류를 구분한다.
- 제출 중 중복 요청을 방지한다.
- 성공, 실패, 취소와 작성 중 이탈 동작을 정의한다.
- 작성한 내용이 예기치 않게 사라지지 않게 한다.
- 기획에 없는 업무 검증 규칙을 AI가 임의로 확정하지 않는다.

정책 결정이 필요한 검증은 구현 가능한 일반 안전 검증과 분리하고 남은 작업에 기록한다.

## 12. 라우팅 및 화면 상태

- URL은 독립적으로 접근하고 복원해야 하는 화면 단위로 만든다.
- 탭, 모달, 아코디언과 같은 화면 내부 상태에 불필요한 URL을 만들지 않는다.
- 링크로 공유하거나 새로고침 후 복원할 가치가 있는 필터는 URL 상태를 검토한다.
- URL parameter와 search parameter의 의미를 문서화한다.
- 존재하지 않는 데이터, 잘못된 URL과 권한 없음 상태를 구분한다.

### 화면 및 URL 목록

| URL | 화면 | 사용자 | 접근 조건 | 구현 상태 |
|---|---|---|---|---|
| `[URL]` | `[화면명]` | `[사용자]` | `[조건]` | `[예정/진행/완료]` |
| `[URL]` | `[화면명]` | `[사용자]` | `[조건]` | `[예정/진행/완료]` |

## 13. 보안 및 개인정보

- 비밀번호, 인증 토큰, API 키와 실제 개인정보를 코드에 저장하지 않는다.
- 민감정보를 오류 메시지, 로그와 분석 데이터에 노출하지 않는다.
- 클라이언트 화면 숨김만으로 권한을 보호하지 않는다.
- 사용자 입력과 외부 데이터를 신뢰하지 않는다.
- 외부 전송, 파일 업로드와 다운로드의 목적과 범위를 확인한다.
- 개인정보 관련 정책이 미확정이면 약한 대안을 임의로 구현하지 않는다.

## 14. 테스트 및 검증

### 프로젝트 명령

실제 프로젝트 명령으로 교체한다.

```text
개발 서버: [작성 필요]
정적 검사: [작성 필요]
타입 검사: [작성 필요]
단위/화면 테스트: [작성 필요]
E2E 테스트: [작성 필요]
production build: [작성 필요]
미리보기: [작성 필요]
```

존재하지 않는 명령을 AI가 임의로 만들지 않는다. 설정 파일과 프로젝트 문서를 먼저 확인한다.

### 검증 기준

- 변경 범위에 맞는 정적 검사와 타입 검사를 실행한다.
- 핵심 업무 규칙과 사용자 상호작용을 테스트한다.
- API 성공, 실패, 빈 응답을 필요한 범위에서 확인한다.
- 주요 사용자 흐름을 통합 또는 E2E 수준에서 확인한다.
- 지원하는 데스크톱과 모바일 크기를 직접 확인한다.
- production build를 확인한다.
- 실행하지 못한 검증은 이유와 후속 조치를 보고한다.

테스트를 삭제하거나 검증 조건을 느슨하게 바꿔 변경 사항을 통과시키지 않는다.

확인하지 못한 항목이 있으면 구현 완료와 검증 완료를 구분해서 보고한다.

## 16. Git 및 파일 변경 안전 규칙

- 작업 시작과 종료 시 변경 파일을 확인한다.
- 관련 없는 사용자 변경 사항을 수정하거나 삭제하지 않는다.
- 명시적인 요청 없이 기록을 삭제하거나 강제로 되돌리지 않는다.
- 자동 포맷이나 코드 생성이 예상보다 넓은 범위를 바꾸면 중단하고 확인한다.
- 빌드 산출물, 비교 이미지와 임시 파일을 저장소에 남기지 않는다.
- 커밋, push, 배포와 외부 시스템 변경은 사용자가 요청한 경우에만 수행한다.

## 18. AI 완료 보고 형식

AI는 작업을 마친 뒤 다음 형식으로 보고한다.

```md
## 구현 결과
- 사용자가 할 수 있게 된 일

## 주요 변경 파일
- 파일 경로: 담당 역할

## 설계 판단
- 적용한 기존 패턴
- 구조와 책임을 나눈 기준
- 새로 결정한 사항과 이유

## 데이터 및 API
- 사용한 API 또는 fixture
- 미확정 계약과 향후 교체 지점

## 검증 결과
- 실행한 명령과 결과
- 확인한 화면 크기와 사용자 흐름

## 남은 작업
- 미구현 기능
- 정책 또는 디자인 결정 필요 사항
- 알려진 제한 사항

## 프론트엔드 인수인계
- 다음 개발자가 확인할 변경 지점
- 수정 시 주의할 의존 관계와 경계
```

단순히 “완료했습니다”라고 보고하지 않는다. 다음 개발자가 코드를 처음부터 조사하지 않아도 변경 목적, 구조, 검증 범위와 남은 위험을 파악할 수 있게 작성한다.
