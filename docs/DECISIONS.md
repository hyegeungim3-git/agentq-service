## D-001 · 린터를 oxlint에서 ESLint로 교체

**결정일** 2026-08-01

**문제** Vite 스캐폴드 기본 린터가 oxlint였다. 속도는 빠르지만 이 프로젝트에서
실제로 났던 결함을 잡는지 확인되지 않았다.

**근거** 이전 프로젝트에서 난 결함 4종을 재현해 두 린터를 대조했다.

| 결함 | oxlint | ESLint (react-hooks v7) |
|---|---|---|
| `rules-of-hooks` 조건부 훅 | O | O |
| `static-components` 렌더 중 컴포넌트 정의 | **X** | O |
| `purity` 렌더 중 `Date.now()` | **X** | O |
| `set-state-in-effect` | **X** | O |

`static-components`는 입력창을 매 렌더 리마운트시켜 '첫 글자만 입력되는' 증상을
만든다. 이전 프로젝트에서 브라우저로 수동 재현해 찾았던 결함이다.

**영향** 린트 시간이 늘어난다. 두 린터를 함께 두지 않은 이유는 §9의
'비슷한 목적의 도구 중복 도입 금지'다.

**교체 조건** oxlint가 위 3개 규칙을 지원하면 재검토한다.

## D-002 · TypeScript 엄격 모드 + 추가 옵션

**결정일** 2026-08-01

**결정** `strict`에 더해 `noUncheckedIndexedAccess`,
`exactOptionalPropertyTypes`를 켠다. 스캐폴드 기본값에는 `strict`조차 없었다.

**근거** 이전 프로젝트에서 도메인 팩 스키마 오작성(배열 자리에 문자열)이
런타임 크래시로만 드러났다. 그 검출을 컴파일 타임으로 옮기는 것이 이 프로젝트의
핵심 목표 중 하나다.

**영향** `exactOptionalPropertyTypes`는 `{ x: undefined }`와 `{}`를 구분한다.
옵션 타입에 `| undefined`를 명시해야 하는 곳이 생긴다(실제로 3곳 겪음).
그 대가로 '속성이 없음'과 '값이 undefined임'이 섞이지 않는다.

## D-003 · 프로젝트 경로에 한글 사용 금지

**결정일** 2026-08-01

**결정** 저장소를 `C:\AgentQ-claude`에 둔다. 한글이 포함된 경로에 두지 않는다.

**근거** 폴더명을 정하기 전에 실측했다.

| 경로 | 모듈 수 | 결과 |
|---|---|---|
| 한글 경로 (최소 프로젝트) | 30 | 통과 |
| 한글 경로 (무거운 의존성) | 2,357 | **크래시 `0xC0000409`** |

아니다. **작을 때는 멀쩡하다가 커지면 죽는다** — 이전 프로젝트가 이 함정을
7주간 못 잡은 이유다.

**영향** 폴더를 옮길 때 경로 제약을 지켜야 한다. `AGENTS.md` §14에도 적었다.

## D-006 · 공통 실행 훅(useAgentRun)·화면 골격(AgentShell) 추출

**근거** 요약·번역·검토를 **각각 만든 뒤** 같은 모양임을 확인하고 뽑았다.
표본 하나로 일반화하면 잘못된 골격이 나오고 둘이면 우연일 수 있다(가이드 §4).

결과는 공통 조상이 없고, 억지로 만들면 화면이 다시 좁혀야 한다.

**적용 범위** 문서 입력형 에이전트에만 쓴다. 대화형(챗봇)은 흐름이 달라
이 골격을 강제하지 않는다.

## D-007 · CI E2E는 dev가 아니라 preview 빌드로 실행

**결정일** 2026-08-02

**문제** 차트를 지연 로딩으로 추가한 직후 E2E 7건이 타임아웃으로 실패했고,
재실행하니 통과했다. 원인은 dev 서버가 모듈을 요청 시점에 컴파일하는 것 —
지연 청크(recharts 379KB)를 여러 워커가 동시에 처음 요청하면 5초 안에 못 준다.

**왜 그냥 넘기지 않았나** '두 번째에 되는' 테스트는 CI에서 무작위로 깨진다.
CI는 항상 콜드 스타트라 재현 조건이 더 나쁘다.

**결정** `CI` 환경변수가 있으면 `npm run build && npm run preview`로 띄운다.
로컬은 반복 실행이 잦아 dev 서버를 유지한다.

**검증** CI 모드로 실제 실행해 54건 통과를 확인했다.

**영향** CI에서 빌드가 한 번 더 돈다(약 1초). 그 대가로 컴파일 타이밍이라는
변수가 사라진다.

## D-008 · package-lock.json은 CI(Linux) 환경에서 만들어 커밋한다

**결정일** 2026-08-02

**문제** 저장소를 만들고 첫 push를 하자 CI가 8초 만에 실패했다.

```text
npm error `npm ci` can only install packages when your package.json and
npm error package-lock.json are in sync.
npm error Missing: @emnapi/runtime@1.11.3 from lock file
```

개발 머신이 Windows다. npm은 **현재 플랫폼에서 쓰이지 않는 패키지의 하위 의존성을
순회하지 않는다.** `@tailwindcss/oxide-wasm32-wasi`가 그 경우라, 그 안의
`@emnapi/runtime`이 lock에 기록되지 않는다. Linux 러너는 그 패키지를 설치 대상으로
보기 때문에 lock과 어긋난다.

**시도한 것과 결과**

| 시도 | 결과 |
|---|---|
| `npm install --package-lock-only` | 추가되지 않음 |
| `npm install --package-lock-only --os=linux --cpu=x64` | 추가되지 않음 |
| Docker / WSL로 Linux에서 생성 | 이 머신에 둘 다 없음 |

**택하지 않은 선택지** CI를 `npm ci` 대신 `npm install`로 바꾸면 바로 통과한다.
하지만 그러면 lockfile 고정이 무의미해지고, 어느 날 의존성이 조용히 올라가
"내 머신에선 되는데"가 된다. 실서비스 준비 저장소에서 포기할 수 없는 성질이다.

**결정** `.github/workflows/lockfile.yml`(workflow_dispatch)에서 lockfile을 만들어
아티팩트로 받아 커밋한다. 워크플로 안에서 `npm ci`까지 돌려 **고쳐졌는지를 스스로
판정**하게 했다 — 통과하지 못하면 실패로 남는다.

의존성을 추가·변경한 뒤 한 번 돌리면 된다.

```bash
gh workflow run lockfile.yml
```

**검증** 재생성한 lock에 `@emnapi/runtime` 1.11.x가 들어왔고 win32 바이너리 항목은
그대로 남았다(+90/-25). Windows에서 `npm ci`와 `npm run verify` 통과,
CI에서 E2E 62건 포함 전체 통과.

**영향** 의존성을 바꿀 때 단계가 하나 늘어난다. 그 대가로 lockfile이 두 플랫폼
모두에서 유효해진다.

**부수 발견** Windows에서 `npm ci`가 `EPERM: unlink`로 실패하면 코드 문제가 아니라
dev 서버가 네이티브 바이너리(`rolldown-binding.win32-x64-msvc.node`)를 잡고 있는
것이다. 해당 프로세스만 종료하고 재실행한다.

## D-009 · 업로드는 만들되, 서버가 없다는 사실을 숨기지 않는다

**결정일** 2026-08-02

**문제** 기존 데모와 대조하니 업로드가 6개 에이전트에 있는데 이 저장소에는 한 곳도
없었다. 그런데 업로드를 붙이려니 걸리는 게 있었다 — **업로드는 파일을 목록에 얹는
일이 아니라 서버가 본문을 뽑아내는 일이다.** PDF·HWP·음성은 브라우저가 열지 못한다.

**택하지 않은 선택지**

| 안 | 왜 안 했나 |
|---|---|
| 올린 파일을 목록에 넣고 기존 fixture 결과를 보여 준다 | 사용자가 올린 계약서에 대해 프레스 작업표준서 요약이 나온다. 발주처 선택·데이터 선택에서 이미 두 번 고친 결함과 같은 것이다 |
| 텍스트 파일만 받아 브라우저에서 읽는다 | 본문은 진짜가 되지만 분석 결과는 여전히 fixture다. 문제가 한 겹 뒤로 밀릴 뿐이다 |
| 업로드를 계속 만들지 않는다 | 클라이언트가 책임지는 부분(형식·용량 검사, 드래그, 접근성)까지 미뤄진다. 그건 서버와 무관하게 지금 확정할 수 있다 |

**결정** 경계를 기준으로 나눈다.

- **클라이언트가 책임지는 것은 지금 만든다.** 형식·용량·빈 파일 검사(`entities/upload`),
  드래그 앤 드롭, 파일 입력 초기화, 오류 표시. 이 코드는 서버가 붙어도 그대로 남는다.
- **서버가 책임지는 것은 경계 함수 하나로 남긴다.** `uploadDocument` / `uploadDataset`가
  지금은 실패를 반환하고, 화면은 그 사유를 그대로 보여 준다.
  "서버에 연결된 뒤에 동작합니다. 지금은 파일을 보낼 곳이 없어 처리할 수 없습니다."

에이전트마다 받는 형식이 다르므로 제약을 네 가지로 정의했다 —
문서(PDF·DOCX·HWP·PPTX·TXT / 50MB), 음성(MP3·WAV·M4A·OGG / 200MB),
스캔(PDF·JPG·PNG·TIFF / 50MB), 데이터(CSV·XLSX / 100MB).
조회형 화면(내규 조회·데이터 조회)에는 올릴 파일이 없어 자리를 그리지 않는다.

**성공 경로를 어떻게 지키나** 지금은 실행되지 않는 코드다. 그래서 `uploadDocument`를
성공으로 바꿔치기한 테스트를 뒀다 — 서버가 문서를 돌려주면 목록에 얹고 바로 선택하는지
확인한다. 배선이 틀린 채로 남아 있다가 서버가 붙는 날 드러나는 일을 막는다.

**검증** 단위 123건 · E2E 76건. 검증을 제거해 보니 해당 테스트가 실패했다.
`accept` 속성은 파일 대화상자의 기본 필터일 뿐 강제가 아니라(끌어다 놓으면 그대로 들어온다),
테스트는 `applyAccept: false`로 그 경로를 확인한다.

**영향** 업로드를 시도하면 반드시 실패한다. 이건 미완성이 아니라 현재 상태를 말하는
것이다. 서버가 정해지면 바뀌는 파일은 `shared/api`의 함수 두 개다.

## D-010 · API 계약은 프론트가 제안하고 백엔드가 확정한다

**결정일** 2026-08-02 (사용자 결정)

**문제** `AGENTS.md` §20의 첫 번째 미결 사항이었다. 계약 주체가 정해지지 않아
`shared/api`의 함수 22개가 전부 `TODO(api-미확정)`으로 남아 있었고, 그 20여 개가
풀리지 않으면 이 저장소의 목적(실제 API를 붙일 수 있는 형태)이 절반에서 멈춘다.

**결정** 프론트가 제안서를 쓰고 백엔드가 확정한다.

**왜 이게 가능한가** 화면이 실제로 무엇을 쓰는지가 이미 타입으로 남아 있다.
`entities/*/model.ts`가 요청·응답 형태이고, `shared/api`가 호출 목록이다.
제안서는 그것을 정리한 것이지 새로 지어낸 것이 아니다.

**무엇을 제안하지 않았나** 인증, 테넌시, 권한 규칙, 감사 로그, 파일 보관 기간,
동시성 상한, 오류 코드 목록. 프론트가 정할 일이 아니라 비워 두고 질문으로 남겼다
(`docs/API-PROPOSAL.md` §3). 추측으로 채우면 '합의된 것'처럼 굳는다.

**한 가지 요청을 명시했다** 보안 등급 필터는 지금 클라이언트가 건다.
실제로는 서버가 걸러야 하고, **거른 건수를 응답으로 알려 달라**고 적었다.
그게 없으면 사용자는 '없다'와 '안 보여 준다'를 구분할 수 없다.

**갈라짐을 막는 법** 제안서에 형태를 다시 적지 않고 TypeScript 타입을 가리킨다.
그리고 `src/shared/api/contract.test.ts`가 양방향으로 확인한다 —
코드의 엔드포인트가 문서에 없으면 실패, 문서의 함수가 코드에 없으면 실패.

**검증** 양방향 탐지를 확인했다. 코드에만 엔드포인트를 추가하면 1건,
문서에만 함수를 남기면 2건이 실패한다.

**영향** `TODO(api-미확정)`의 제거 조건이 'API 명세 확정'에서
'백엔드가 제안서를 확정'으로 바뀌었다. 22개 함수 전부에 구체 엔드포인트가 붙었다.

## D-011 · Recharts를 걷어내고 차트를 직접 그린다 (D-005 뒤집음)

**결정일** 2026-08-08

> ⚠️ **이 결정은 사용자 승인을 받은 D-005를 뒤집은 것이고, 뒤집을 때 승인을 먼저
> 받지 않았다.** AGENTS.md §7("승인 없이 라이브러리를 설치하지 않는다")의 취지는
> 제거에도 그대로 적용된다 — 의존성을 바꾸는 결정이기 때문이다. 절차를 어겼다는
> 사실을 남긴다. 사용자가 되돌리기를 원하면 커밋 하나를 되돌리면 된다.

**문제** 첫 화면 코드를 나눈 뒤 남은 것 중 제일 큰 덩어리가 차트였다.
꺾은선 하나·막대 하나에 370KB(gzip 105KB). 전체 전송량의 27%였다.

**D-005가 직접 SVG를 물리친 근거와, 그 근거가 지금은 성립하지 않는 이유**

| D-005의 근거 | 지금 |
|---|---|
| 축을 다 만들어야 한다 | 눈금 5개를 사람이 읽는 단위로 올리는 함수 하나(12줄) |
| 툴팁을 만들어야 한다 | `title` 속성이면 된다 — 브라우저가 그린다 |
| 반응형을 만들어야 한다 | 글자는 HTML, 늘어나는 도형만 SVG로 나누니 필요 없어졌다 |
| SVG라 E2E에서 값 검증이 가능하다 | **차트로 값을 검증하지 않는다.** 같은 수치를 표가 내고 검사는 표를 본다 |

마지막 줄이 결정적이다. **차트는 데이터를 지고 있지 않다** — 호출부가 같은 수치를
표로 함께 내주고(캡션 포함) 차트는 `aria-hidden`이다. 라이브러리가 주는 것 중
실제로 쓰는 것이 거의 없었다.

**결정** recharts 제거. `src/widgets/charts/AnalysisCharts.tsx`에서 직접 그린다.
글자는 HTML, 격자선·꺾은선만 SVG(`preserveAspectRatio="none"` + `non-scaling-stroke`).
막대는 HTML만으로 충분하다.

**대가로 잃은 것** 애니메이션, 브러시·줌, 축 자동 회전. 지금 화면에서 안 쓰던 것들이다.
쓸 일이 생기면 이 결정을 다시 뒤집는 편이 낫다 — 직접 그린 것에 그 기능을 덧대는
것보다 싸다.

**직접 그리자마자 낸 결함** 최대값을 4로 나눠 눈금이 0.15·0.45가 되고 글자는
반올림돼 0.2·0.5로 적혔다. **격자선과 숫자가 어긋난 축**이다. 검사는 전부 통과했다 —
차트가 그려졌는지만 봤기 때문이다. 스크린샷을 눈으로 보고 잡았고, 지금은
`AnalysisCharts.test.tsx`가 눈금 글자를 도로 숫자로 읽어 간격이 일정한지 본다.

**측정** 차트 청크 370KB→3KB(gzip 105KB→1KB), 전체 380KB→276KB gzip.
확인: 라이트·다크 × 넓은 화면·375 스크린샷, 라이브에서 `recharts` 흔적 0건.

**영향** `package.json`에서 recharts 삭제(lockfile은 `lockfile.yml`로 재생성).
D-005는 이 결정으로 대체된다.

## D-012 · 코드를 세 겹으로 나눈다 — 화면이 아니라 **사용자가 고르는 경계**로

**결정일** 2026-08-08

**문제** 첫 화면 하나에 전부 들어 있었다. 실측 1021KB(gzip 262KB) — 관리자 44화면,
에이전트 13종, 발주처 넷의 업무 데이터가 모두 첫 방문자에게 갔다.

**어디서 끊었나 — 기준은 '사용자가 직접 고르는 곳'이다**

| 겹 | 경계 | 근거 |
|---|---|---|
| 1 | 관리자 / 에이전트 | 포털에서 **눌러서** 들어가는 곳. 안 누르면 영영 필요 없다 |
| 2 | 관리자 **섹션** 5개 | 사이드바에 **눈에 보이는** 구분. 한 섹션 안에서는 이미 받은 것이라 기다림이 없다 |
| 3 | 차트 | D-011 참조 |

화면마다 나누지 않은 이유: 44개 요청이 된다. 안 나누면 처음에 다 받는다.
섹션은 그 사이이고, **사용자가 이미 인지하는 구분**이라 기다림이 생기는 자리가 납득된다.

**결과**

| | 처음 | 지금 |
|---|---|---|
| 첫 화면 | 270KB gzip | **196KB gzip** |
| 관리자 진입(시스템 현황) | 첫 화면에 포함 | AdminApp 5KB + 대시보드 6KB = **11KB** |
| 에이전트 13종 | 첫 화면에 포함 | 22KB — 허브에서 고를 때 |

**지키는 방법을 둘로 나눴다**
- **크기** — `npm run budget`(CI 단계). `dist/index.html`이 가리키는 자산을 전부 더한다
- **시점** — e2e가 실제 요청을 본다. 파일이 나뉘어 있어도 어디선가 정적으로 import하면
  첫 화면이 같이 받는데, 그건 크기만으로는 안 드러난다

**이 검사에서 실제로 난 결함** 처음 예산 검사는 `index-*.js` 하나와 CSS만 셌다.
섹션을 나누자 번들러가 공통 코드를 `pack-*.js`(gzip 90KB)로 빼고 `modulepreload`로
걸었는데, **계산에서 빠져 194KB가 98KB로 줄어든 것처럼 보였다.** 숫자로만 보이는 것을
지키라고 만든 검사가 숫자를 틀리게 낸 것이다. 지금은 진입 HTML을 읽어 더한다.

**남은 것** `pack-*.js` 90KB gzip — 발주처 넷의 업무 데이터가 **전부** 첫 화면에 있다.
한 번에 한 발주처만 쓰므로 같은 종류의 낭비이고, 지금 첫 화면의 46%다.
다만 `fetchDomains()`가 포털 목록을 그리려고 팩을 읽으므로, 목록용 요약과 본문 데이터를
가르는 작업이 먼저다. **아직 하지 않았다.**

## D-013 · 발주처 업무 데이터를 고를 때 받는다

**결정일** 2026-08-08

**문제** 발주처 넷의 업무 데이터가 **첫 화면에 통째로** 실려 있었다(gzip 90KB,
첫 화면의 46%). 크기 문제이기 전에 **테넌시 문제**다 — 공공기관 담당자의 브라우저에
병원 데이터가 통째로 내려가 있었다는 뜻이다.

**원인은 내가 앞서 적은 것과 달랐다** — `fetchDomains()`가 팩을 읽어서가 아니다
(`domains.ts`는 팩을 import하지 않는다). 진짜 원인은 `shared/api/*`가 전부 `pack.ts`를
거치고, 그 파일이 팩 넷을 **정적으로** import한 것이다. 추측으로 적은 원인을
그대로 뒀다면 엉뚱한 곳을 고쳤을 것이다.

**바꿀 수 있었던 이유** `withPack`/`withPackOf`가 처음부터 `Promise`를 돌려주게
설계돼 있었다(D-003의 '지금 동기지만 반환 타입은 Promise로 고정한다'). 그래서
**경계 함수 116곳과 호출부는 한 줄도 안 바뀌었다.** 미리 열어 둔 비동기 경계가
3개월 뒤에 값을 한 셈이다.

**결정** `PACKS` 정적 맵 → `PACK_LOADERS` 동적 import + 한 번 받은 것은 캐시.
`currentPack()`·`withPackOf()`·`packStatuses()`가 비동기가 됐다.

**대가** 화면 내용이 한 박자 늦게 그려진다. 서버가 붙으면 어차피 그렇게 되므로
**현실에 가까워진 것**이지 나빠진 것이 아니다. 다만 두 자리를 손봐야 했다.
 - `useOrchestration` — `undefined`(아직 모름)와 `null`(릴레이 없음)을 갈랐다.
   합쳐 두면 받는 동안 화면이 '릴레이가 아직 없습니다'라고 **거짓말**한다
 - 검사 셋 — 기다리지 않고 단정하던 것을 대기로 바꿨다(덜 그려진 화면을 훑고 있었다)

**관리자 팩 현황 화면만은** 넷을 다 받는다. 넷을 비교해 보여 주는 것이 그 화면의
일이라 피할 수 없고, 관리자 안에서만 일어난다.

**측정** 첫 화면 196KB → **106KB gzip**(−46%). 팩은 고를 때 11~23KB.

**지키는 법** `e2e/a11y-census.spec.ts`의 '고른 발주처의 업무 데이터만 받는다'가
**크기가 아니라 무엇을 받았는지**를 본다. 정적 import를 되넣으면 '분야를 고르기도 전에
업무 데이터를 받고 있다'로 실패한다(확인함).
