# 재구축 기록 — 무엇을 왜 다르게 만들었나

> 이전 데모(`qagent-platform`)를 `agent-rules` 가이드에 맞춰 다시 세운 기록이다.
> **무엇이 달라졌는지, 왜 그렇게 했는지**를 남긴다. 결정의 배경은 `DECISIONS.md`,
> 앞으로 만들 것은 `SCOPE-PLAN.md`, API 제안은 `API-PROPOSAL.md`에 있다.
>
> 이 문서는 작업이 끝날 때마다 갱신한다. 낡으면 지운다.

## 1. 왜 다시 만들었나

이전 데모는 백엔드 없이 전부 mock으로 도는 시연물이었다. 그대로 실서비스로 가면
**API를 붙이는 순간 화면을 전부 다시 써야 한다.** mock이 UI 표시용 형태였기 때문이다.

```js
// 이전 데모
{ label: '수집 항목', value: '4,380건', sub: '...', tone: 'base' }
```

`'4,380건'`은 이미 포맷된 문자열이고 `tone: 'base'`는 색이다. 서버는 둘 다 주지 않는다.
서버는 `4380`을 주고 천 단위 구분과 색은 화면이 정한다.

목적은 하나다 — **실제 API를 붙일 수 있는 형태로 다시 세우는 것.**
화면·콘텐츠는 자산으로 가져오되 데이터 형태는 옮기지 않는다.

## 2. 구조가 달라진 점

| | 이전 데모 | 지금 |
|---|---|---|
| 언어 | JavaScript | TypeScript strict (`noUncheckedIndexedAccess`·`exactOptionalPropertyTypes`) |
| 화면 파일 | `UserApp.jsx` 2,173줄 → 모듈 분리(진행 중이었음) | 영역별 분리 (`app`/`pages`/`widgets`/`features`/`entities`/`shared`/`fixtures`) |
| 데이터 | 화면이 mock을 직접 읽음 | **`shared/api` 경계를 반드시 통과** — 서버는 이 안에서만 교체 |
| mock 형태 | UI 표시용 문자열·색 | **API 응답이 될 수 있는 형태**(원시 값·코드·ID) |
| 스키마 | 없음 (런타임에 깨짐) | `entities/*/model.ts` 타입 — fixture가 타입을 만족해야 컴파일 통과 |
| 린트 | 없음(명령은 있으나 CI에 없어 오류 71건 누적) | ESLint + react-hooks v7, **CI 게이트** |
| 테스트 | 없음 | 단위/화면 190여 건 + E2E 110여 건(데스크톱·모바일) |
| CI | 없음 | lint → typecheck → test → build → E2E, 통과해야 배포 |
| 배포 | 수동 | GitHub Pages, verify 통과분만 |

### 경로 별칭을 쓰는 이유

`@shared` 같은 별칭은 취향이 아니라 **의존 방향을 눈에 보이게** 하려는 것이다.
`../../../`는 어느 층에서 어느 층을 부르는지 숨긴다. `shared`가 특정 페이지를 알면 안 된다.

### `<main>`은 화면이 갖는다

셸은 `<nav>`와 배치만 맡는다. 셸에도 `<main>`을 두면 화면마다 main이 둘이 되어
보조기기가 본문을 못 찾는다.

## 3. 화면이 달라진 점 — 공통 원칙

이전 데모와 가장 크게 다른 것은 **AI가 못 한 것을 드러낸다**는 점이다.
에이전트마다 "이것만은 숨기면 안 되는 것"을 하나씩 정하고 화면이 먼저 말하게 했다.

| 화면 | 숨기지 않는 것 |
|---|---|
| 문서 요약 | 압축률과 원문 대조 안내 |
| 번역 | 역번역 일치도가 낮은 문장, 사전에 없어 번역 못 한 문장 |
| 사전 검토 | 심각도 높음이 남아 있으면 결재 상신을 권하지 않음 |
| 챗봇 | 근거를 못 찾으면 답을 지어내지 않음 + 출처 원문 열람 |
| 보고서 | 사람이 채워야 하는 칸(`pendingFields`) |
| 회의록 | 담당·기한 미정 항목, 논의되지 않은 안건, 명단에 없는 발언자 |
| 지식 검색 | 필터에 걸려 빠진 건수 — '없다'와 '안 보여 준다'는 다르다 |
| OCR | 신뢰도 낮은 줄, 설정 때문에 나빠졌다는 사실 |
| 데이터 조회 | AI가 가정한 조건, SQL로 못 옮긴 표현 |
| 기준정보 표준화 | AI로 해결 안 되는 660건과 표준화율 상한 86% |
| 데이터 분석 | 분석에 쓰이지 못한 데이터(적용률 71%) |
| 안전관리계획 | 대책 뒤에 남는 잔여 위험 |
| 오케스트레이션 | 끝까지 갔어도 사람이 확인할 지점 합계 |
| 관리자 대시보드 | 실측이 아니라 예시 값이라는 사실 · 주의 상태의 사유와 조치 · 파드 재시작 횟수 |
| 관리자 메뉴 | 아직 안 만든 화면 19개를 감추지 않고 '준비 중'으로 표시 |
| 사용자 목록 | 접속 이력이 없는 계정 · 상태 변경이 저장되지 않았다는 사실 |
| 승인 관리 | 며칠 기다렸는지 · 신청 사유를 안 적었다는 사실 |
| 할당량 | 한도 초과분 · 집계 기준 시각 · 무제한 계정을 0%로 그리지 않음 |
| 접근 로그 | **로그에 남지 않는 것** — 목록만 보면 '여기 있는 게 전부'로 읽힌다 |
| 접근권한·차단 | 만료돼 더 이상 막지 않는 규칙 |
| LLM 설정 | 모델을 왜 껐는지 · 이 모델로 나가는 답변이 무엇인지 |
| 신뢰성 관리 | **아직 안 잰 효과** — 0으로 세면 효과가 없어 보이고 평균이 무너진다 |
| 신뢰성 관리 | 가드레일을 껐을 때 무엇이 통과하게 되는지 |
| AI 품질 관리 | 손봐야 하는 답변의 비율 · 사용자 피드백이 이 브라우저 것뿐이라는 사실 |
| 이용 이력 | 질의 본문을 남기지 않는다는 사실과 그래서 못 하는 것 |
| 이용만족도 | **답하지 않은 사람 수** — 평균은 답한 사람만의 평균이다 |
| 이용 통계 | 평균 응답시간이 성공한 요청만 센 값이라는 것 |
| 통계 리포트 | 지금 못 만드는 항목과 그 이유 |
| 통합 로그 | 접근 로그와 같은 데이터라는 사실 · 질의 본문 미보관 |
| 사용량 | 지금 속도면 며칠 뒤 한도에 닿는지 · 금액이 없는 이유 |
| 콘텐츠 관리 | 여기 있는 것이 곧 포털에 보이는 것이라는 사실 |
| HR 연계 | **처리하지 못한 퇴직** — 그 계정은 지금 접속이 열려 있다 |
| API 관리 | 키를 화면에 두지 않는 이유 · 베타·중지 API가 왜 그런지 |
| 프롬프트 | 바꿨을 때 무엇이 달라지는지 |
| 연계 SW | 끊기면 무엇이 멈추는지 (정상인 것도 함께) |
| 가드레일 | **경고만 하고 통과시킨 건** — 그건 실제로 나갔다 |
| AI 기본법 | 이 화면이 법적 판단을 내리지 않는다는 것 · 판정이 안 끝났는데 운영 중인 시스템 |
| 지식 관리 | **등록됐는데 검색에 안 잡히는 문서**와 그 이유 · 색인 뒤 바뀐 문서 · 재색인 미완료 |
| 에이전트 운영 | 실패율 · 근거 문서에 빈틈이 있는 에이전트(고칠 곳이 어디인지) · 안 쓰는 에이전트 |
| 애플리케이션 | 못 여는 앱과 그 이유 · 발주처별 노출이 포털과 같은 기준이라는 것 |
| 도메인 팩 | 채움 비율이 아니라 **비어 있는 항목의 이름**과 그중 필수인 것 |
| 도구 · 배포 | 끊긴 도구 때문에 못 도는 에이전트 · 검증에만 있고 운영에 안 나간 버전 |
| 데이터 관리 | 학습·평가 겸용 데이터셋 · 출처를 모르는 데이터 · 개인정보를 어떻게 처리했는지 |
| 개발 환경 | 놀면서 GPU를 잡고 있는 작업 공간 · 회수 기준이 없다는 사실 |
| 모델 레지스트리 | **계보가 끊긴 모델** · 평가 없이 운영 중인 모델 |
| 학습 · 튜닝 | 학습 데이터 기록 없이 돈 작업 |
| 모델 평가 | **부풀려진 점수를 순위에서 뺀 것과 그 이유** |
| 태스크플로우 빌더 | **사람 확인 없이 실행되는 에이전트** · 없는 능력도 함께 표시 |
| 시나리오 빌더 | 켜져 있지만 끊긴 도구 때문에 못 도는 시나리오 |
| 앱 인스턴스 | 내려간 이유 · 열려 있는데 아무도 안 쓰는 앱 |
| RAG 파이프라인 | **어느 단계에서 몇 건이 왜 떨어졌나** · 아직 안 끝난 실행 |
| 벡터 DB | **차원이 달라 섞어 쓸 수 없는 컬렉션** · 어느 영역에도 안 붙은 것 |
| 자동 적재 | 스케줄은 도는데 실패한 소스 · **성공했는데 0건**인 소스 |
| 평가 지표 | **이 벤치마크가 우리 업무와 얼마나 가까운가** · 업무와 다른 지표로만 잰 모델 |
| 감사 추적 | **'이행했다'와 '증명할 수 있다'의 차이** · 아무 데도 기록이 안 남는 책무 |
| MCP 서버 | 사외로 나가는 서버 · 주소를 표시하지 않는 이유 |
| 공유 볼륨 | 곧 찰 볼륨(차면 학습이 멈춘다) · 두 달 넘게 방치된 볼륨 |
| 워크플로우 | **한 번도 안 탄 분기** · 실패가 몰린 노드 · 검토 없이 실행까지 가는 흐름 |
| 학습 · 튜닝 | 설정이 없어 **재현할 수 없는** 작업 |
| 사업장 지표 지도 | 값이 없는 사업장과 그 이유 — 평균이 전사 평균이 아니라는 사실 |
| 라이브 지표 | 실측이 아니라 예시 값이라는 사실 |
| 판단 근거 | 이 답변만으로 결정하면 안 되는 이유 |

### 두 번째 원칙 — 고른 것이 결과를 바꾼다

이전 데모에는 **결과를 바꾸지 않는 설정**이 여럿 있었다. 옮기면서 전부 실동작으로 고쳤다.
아래는 재구축 과정에서 실제로 발견해 고친 것들이다.

| 발견 | 무엇이 문제였나 |
|---|---|
| 발주처 선택 | 공공을 골라도 제조 문서(`프레스_작업표준서`)가 그대로 나왔다 |
| 데이터 분석 | 무엇을 골라도 같은 불량률 추이가 나왔다 (대상도 PDF·음성이었다) |
| 번역 언어 | 일본어·중국어를 골라도 영어 번역문이 나왔다 |
| OCR 설정 | 언어·표 추출·처리 모드·결과 형식이 결과를 바꾸지 않았다 |
| 보고서 | 문체·분량이 없었고 직접 입력 칸도 없었다 |
| 사이드바 항목 | 워크스페이스·공지사항·사용 가이드가 눌러도 아무 일이 없었다 |

## 4. 의도적으로 다르게 만든 것

가이드가 "미확정 API의 운영 계약을 임의로 만들지 않는다"고 해서, 이전 데모에 있던 것 중
**지어내야만 옮길 수 있는 것**은 형태를 바꿨다.

| 이전 데모 | 지금 | 이유 |
|---|---|---|
| 보안 게이트웨이 설정 탭 | 데이터 취급 현황 | 운영 정책이 미정이라 설정 화면을 만들면 다 정해진 것처럼 보인다. 지금 사실인 것만 적고 미정 개수를 먼저 말한다 |
| MCP 호출 로그(grpc 주소·토큰 수) | 각 단계가 부르는 데이터 경계 함수 | 인프라 주소를 지어내지 않는다. 서버가 붙으면 그 자리가 엔드포인트가 된다 |
| 파일 업로드(성공) | 검사까지 동작, 전송은 실패 | 서버가 파싱해야 본문이 나온다. 성공한 척하면 남의 문서 분석 결과를 보여 주게 된다 |
| 발주처 4종 모두 선택 | 제조만 선택 가능, 나머지는 '업무 데이터 준비 중' | 업무 데이터가 하나뿐인데 고르게 두면 고르는 행위에 의미가 없다 |
| 지도(지리 좌표 위 표시) | 배치 도식 + '실제 지리 좌표 아님' | 좌표 데이터가 없다. 지도처럼 보이는데 위치가 틀리면 그게 제일 위험하다 |
| 표시 언어 전환(전면) | 화면 틀만 전환, 콘텐츠는 원문 유지 | 규정 조항을 기계 번역하면 그게 원문인 줄 알고 인용하게 된다. 원문을 보여 주는 이유와 같은 이유다 |
| 관리자 메뉴 74개를 전부 노출(빈 화면 포함) | 만든 것과 준비 중을 구분해 표시 | 감추면 기능이 없는 줄 알고, 껍데기를 두면 만든 줄 안다. 눌렀을 때 무엇이 언제 오는지 말한다 |
| 서비스 상태 `Warning` 배지 | 사유 + 조치 문장 | 상태를 아는 것과 조치할 수 있는 것은 다르다 |
| 계정 정지·승인이 동작하는 관리자 | 조회는 동작, 변경은 실패를 그대로 알림 | 화면에서만 바꾸면 정지시킨 줄 알고 닫는데 그 계정은 살아 있다. 업로드와 같은 처리(D-009) |
| 정확도 향상 `-` 표기 | '측정 전' + 평균에서 제외 | `-`나 `0`은 '효과 없음'으로 읽힌다. 안 잰 것과 효과가 없는 것은 다르다 |
| 신뢰성 관리의 RAG 파이프라인 탭 | 두지 않음 — 지식 관리(P3)에서 다룸 | 같은 것을 두 화면에 두면 어느 쪽이 진짜인지 알 수 없게 된다 |
| 이용 이력에 질의 본문 표시 | 본문 없음 + 왜 없는지 | 접근 로그가 '질문 본문은 남기지 않는다'고 말하고 있었다. 두 화면이 다른 말을 하면 어느 쪽이 사실인지 알 수 없다. 보관 여부는 백엔드가 정한다(§3-7) |
| 접속 로그를 두 화면에 각각 보관 | 한 데이터를 두 관점으로 | 사용자 관리는 계정 관점(거부 먼저), 통합 로그는 운영 관점(종류별). 복제하면 같은 시각의 같은 행위가 서로 다르게 적힌다 |
| 콘텐츠 관리가 자체 목록을 가짐 | 포털과 같은 자원 | 따로 두면 '여기서 고쳤는데 포털에 안 나오는' 상태가 생긴다 |
| 콘텐츠 관리의 설문 탭 | 안내만 — 서비스 분석에서 다룸 | 같은 것을 두 화면에 두면 어느 쪽이 진짜인지 알 수 없다 |
| 앱 유형별 메뉴 3개(채팅·보고서·데이터 분석) | 화면 하나 + 유형 필터 | 표 모양이 같아 세 벌 만들 이유가 없다. 필터가 결과를 실제로 바꾸므로 기능은 그대로다 |
| 벡터 검색 시뮬레이터 | 넣지 않음 | 실제 벡터 DB에 질의해야 결과가 나온다. 서버 없이 흉내 내면 '검색해 봤다'는 착각만 준다 |
| 벤치마크 점수를 한 표에 나열 | 무엇을 재는지·업무 근접도를 점수보다 먼저 | 점수만 나란히 두면 위키 독해 잘하는 모델을 사내 문서 QA용으로 고르게 된다 |
| 학습 유형별 메뉴 4개 | 화면 하나 + 유형 필터 + **유형별 설정** | 표 모양이 같아 네 벌 만들 이유가 없다. 대신 유형마다 다른 설정을 보여 준다 — 설정이 없으면 같은 결과를 다시 만들 수 없다 |
| 태스크플로우 배포 별도 화면 | 도구·배포의 배포 대상에 '에이전트 정의' 추가 | 배포는 한 화면에서 봐야 무엇이 아직 안 나갔는지 한눈에 보인다 |
| 시스템 설정 하위 4개 | 화면 2개 + 관리 홈 진입점 | '공지사항'은 콘텐츠 관리와, '시스템 모니터링'은 대시보드 시스템 현황과 같은 화면이었다. 두 벌 만들지 않고 관리 홈 카드가 그 화면으로 간다 — 진입점은 그대로 남는다 |
| API 키 목록·재발급 | 키를 아예 표시하지 않음 | 목록에 있으면 화면을 여는 사람 모두가 모든 키를 갖게 되고, 화면은 캡처되고 공유된다. 잃어버렸으면 재발급이 정답이다 |
| 가드레일 규칙 목록(두 화면) | 신뢰성 관리=설정, 가드레일=이력 | 같은 목록을 두 화면에 두면 어느 쪽이 진짜인지 알 수 없다. 이전 데모의 가드레일 메뉴는 눌러도 대시보드로 떨어지는 죽은 메뉴였다 |
| 차단 이력에 걸린 원문 표시 | 종류와 건수만 | 개인정보를 가리려고 만든 규칙의 이력에 그 개인정보가 그대로 있으면 앞뒤가 안 맞는다 |
| 지식 관리(이전 데모엔 화면 없음) | 새로 설계 | 메뉴는 있었지만 눌러도 대시보드로 떨어지는 죽은 메뉴였다. 화면이 없으니 옮길 것도 없어 이 제품에 필요한 것으로 새로 세웠다 |
| 관리자의 에이전트 목록 | 포털과 같은 카탈로그(`entities/agent/model.ts`)를 읽고 운영 정보만 얹음 | 목록을 따로 가지면 '관리자에는 있는데 포털에는 없는 에이전트'가 생긴다. 테스트가 두 곳의 id 집합이 같은지 확인한다 |

### 다크 스킨을 화면마다 칠하지 않은 이유

`dark:` 접두사를 화면마다 붙이는 방법 대신 **팔레트 변수 한 벌만 뒤집었다**
(`src/index.css`). Tailwind v4는 모든 색 유틸리티가 `var(--color-*)`를 참조한다.

접두사 방식은 새 화면이 생길 때마다 빠뜨리고, 빠뜨린 자리는 밝은 채로 남는다.
변수 방식은 앞으로 만들 관리자 74개 화면도 자동으로 따라온다.
값은 반대편 색조를 그대로 써서 밝기 대비를 보존한다 — 임의로 어둡게 칠하면 대비가 무너진다.

## 4-1. 겉모습을 이전 데모에 맞춘 것 (2026-08-03)

**정직하게 적어 둔다.** 기능은 다 옮겼지만 **겉모습은 옮기지 않았었다.**
로고도 브랜드 색도 아이콘도 없었고, 화면은 회색 카드와 검은 버튼뿐이었다.
"실서비스 붙일 수 있는 구조"를 우선하느라 뒤로 밀린 것이지, 의도한 차이가 아니었다.
나란히 놓고 보면 발주처에게는 이전 데모 쪽이 더 완성된 물건으로 보였다.

옮긴 것과, 옮기면서 정한 규율은 이렇다.

| 옮긴 것 | 어떻게 |
|---|---|
| OCUBE 심볼 | 이전 데모의 SVG를 **그대로** 옮겼다. 다시 그리지 않았다 — 문구를 새로 썼다가 모바일 진입점 20곳을 깨뜨린 적이 있다 |
| 발주처 브랜드 색 | `--color-brand` **변수 하나**를 셸이 꽂고, 화면은 `bg-brand`·`text-brand`로만 부른다 |
| 아이콘 | `lucide-react` — 탭·관리자 메뉴·프로필. 상위 메뉴에만 붙였다(하위까지 붙이면 24개가 60개로 보인다) |
| 탭 스위처 | 세로 목록 → 한 덩어리 세그먼트. 셋이 나란해야 '옆에 무엇이 있는지'가 보인다 |
| 상단 바 | 관리자는 `구역 · 상위 · 화면` 길잡이. 메뉴가 55개라 제목만으론 위치를 모른다 |
| 오른쪽 근거 패널 | 이전 데모의 'RAG 연동 문서' 자리 |
| 에이전트 13종 | 허브 카드와 화면 머리 — 아래 §4-2 |
| 결과 화면 | 결과 절 머리·AI 고지 — 아래 §4-3 |

### 브랜드 색을 변수 하나로 둔 이유

다크 스킨을 팔레트 변수 한 벌로 처리한 것과 같은 이유다. 화면마다
`style={{ backgroundColor: domain.brandColor }}`를 뿌리면 **새 화면을 만들 때마다
빠뜨리고, 빠뜨린 자리만 회색으로 남는다.** 실제로 그랬다 — 셸·포털·허브만 칠해져
있었고 나머지 50여 화면은 색이 없었다.

지금은 셸이 `brandVars(domain.brandColor)` 하나를 꽂는다. 포털은 발주처가 여럿이라
카드마다 꽂는다(변수는 상속되므로 카드 안쪽만 그 색이 된다).

### 근거 패널은 모양만 옮기고 내용은 바꿨다

이전 데모의 패널은 문서 목록을 보여 줬다. 그런데 **목록에 있다고 답할 수 있는 것은
아니다** — 색인이 안 된 문서는 사용자에게 '없다'고 답하고, 사용자는 그걸 구분할 방법이
없다. 그래서 여기서는 찾을 수 있는 건수를 먼저 세고, 등록됐는데 못 찾는 것이 있으면
그 자리에서 말한다. 관리자의 지식 관리 화면과 같은 데이터를 같은 기준으로 본다.

### 검사로 지킨다

스킨은 시간이 지나면 조용히 갈라진다. 급한 화면 하나에 `#0F766E`를 직접 쓰면
그 화면만 발주처를 안 따라가고, 아무도 모른다. 그래서 두 가지를 기계로 막았다.

- `scripts/design-tokens.test.ts` — 임의 색 리터럴 금지, `brandColor`를 읽는 곳은 두 곳뿐
- `e2e/skin.spec.ts` — **계산된 배경색**을 발주처 팩의 값과 대조(클래스가 붙었는지가 아니라)

둘 다 결함을 다시 넣어 실제로 실패하는지 확인했다.

## 4-2. 에이전트 13종 (2026-08-03)

발주처가 가장 오래 보는 화면이라 따로 손봤다.

### 허브 카드 — 배지를 늘어놓지 않는다

이전 데모의 카드는 화려했다. 실행 횟수, 순위(#01), 즐겨찾기 별, 모델 칩, 단계 원.
그중 **판단에 쓰이는 것**만 옮겼다.

| 옮긴 것 | 왜 |
|---|---|
| 능력 배지 | 무엇을 근거로 답하는지 — 문서 근거(RAG)인지 직접 응답인지 |
| 밟는 단계 | 눌러 보기 전에 무엇을 하는지 알 수 있다 |
| **사람 확인 지점** | 없으면 결과가 그대로 나간다 |
| 안 옮긴 것 | 실행 횟수·순위·별 — 서버가 없어 지어내야 하는 값이다 |

단계·배지는 **관리자의 '태스크플로우 빌더'와 같은 정의**(`agentdef`)를 읽는다.
복제하지 않았다 — 거기서 단계를 고치면 여기 카드도 함께 바뀐다.

배지를 나열만 하면 `RAG·A2A·실행형`이 많을수록 좋아 보인다. 정작 위험한 것은
**확인 없이 결과가 나가는 것**이라, 카드 아래에 그것을 따로 적는다.
지금 13종 중 **7종**이 '사람 확인 지점 없음'이고, 그중 안전관리계획 수립은 실행형이다
— 답을 내놓는 데서 끝나지 않고 무언가를 실제로 한다.

### 화면 머리를 하나로

절반은 공통 셸(`AgentShell`)을 쓰고 절반은 각자 만들고 있었다. 그래서 어떤 화면은
`← 돌아가기` 글자 버튼이고 어떤 화면은 아이콘이 없었다. 셸을 안 쓰는 화면(질문
입력형·릴레이)을 위해 `AgentPageHeader`를 뽑아 **13종이 같은 머리**를 쓴다.
아이콘은 허브 카드와 **같은 것**을 쓴다 — 카드에서 본 모양이 그대로 나와야 한다.

### 카드 이름이 길어져 다른 에이전트와 겹쳤다

카드 전체를 버튼으로 두고 그 안에 단계까지 넣었더니, 버튼의 접근성 이름이
`표준 보고서 작성 … 실적 데이터 조회 › …`가 되어 **'데이터 조회' 에이전트와 겹쳤다.**
E2E가 먼저 잡았다(`strict mode violation`). 보조기기에도 같은 문제다 —
이름은 짧아야 하고 설명은 따로 읽혀야 한다.

지금은 버튼이 **제목만** 갖고, 겹침(`after:inset-0`)으로 카드 전체를 덮는다.
설명은 `aria-describedby`로 잇는다.

### 검사로 지킨다

`e2e/skin.spec.ts`가 13종을 훑으며 제목·돌아가는 길·가로 스크롤을 본다.
눈으로 13번 보는 대신이다. 돌아가는 길을 하나 지워 실제로 실패하는지 확인했다.

## 4-3. 결과 화면 (2026-08-05)

에이전트를 돌리고 나서 보는 자리다. 발주처가 'AI가 무엇을 했나'를 실제로 확인하는 곳.

### 입력과 결과가 같은 모양이었다

문서 고르기·옵션·결과가 전부 같은 흰 카드였다. 스크롤하다 보면 **어디부터가
모델이 만든 것인지** 알 수 없다. 결과 절에만 브랜드 색 머리 띠를 뒀다.

### AI 고지가 화면에서 가장 안 보였다

`text-slate-400` 한 줄이었다. **규제상 붙여야 하는 문구**(AI 기본법 제31조
생성물 표시)인데 가장 흐린 자리에 있었다. 아이콘 + 테두리 있는 블록으로 세웠다.

### 셸을 안 쓰는 화면 3곳도 같은 틀로

지식 검색·데이터 조회·내규 조회는 각자 결과를 그리고 있었다. `ResultSection`으로
바꿔 13종이 같은 모양이 됐다. 데이터 조회는 절이 둘이라(표·근거) 고지는 한 번만 붙인다 —
같은 문구를 두 번 붙이면 오히려 안 읽는다.

### 검사로 지킨다

`scripts/result-notice.test.ts`가 센다.

- 결과 절을 쓰는 화면에 `notice`가 없으면 실패
- 고지가 `AI가 …`로 시작하지 않으면 실패 — '결과입니다'로만 쓰면 누가 만든 건지 모른다

고지에서 주어를 빼 보고 실제로 실패하는지 확인했다.

## 4-4. 두 번째 발주처 (2026-08-05)

이 제품의 핵심 주장은 **발주처를 갈아끼울 수 있다**는 것이다. 그런데 지금까지는
그걸 보여 줄 수 없었다 — fixture가 전부 제조(한빛정밀) 하나뿐이라, 다른 발주처를
고르면 제조 문서가 그대로 보였다. 그래서 포털이 아예 못 고르게 막아 두었다.

### 구조 — 발주처를 경계가 든다

`shared/api/tenant`가 지금 발주처를 들고, `fixtures/packs`가 그 발주처의 업무
데이터를 준다. 화면은 요청마다 발주처를 넘기지 않는다 —
제안서 §3-2에서 백엔드에 헤더를 권한 것과 같은 방식이다.

**기본값을 두지 않았다.** 발주처가 안 정해졌으면 아무 발주처 것을 주는 대신
'이 발주처의 업무 데이터가 아직 없습니다'라고 답한다.

꽂는 자리는 렌더도 effect도 아니고 **셸로 들어가는 길목**이다. effect에서 꽂으면
자식 effect가 부모보다 먼저 돌아 아직 발주처가 안 정해진 채로 데이터를 부른다.

### 13종을 첫날부터 쓰는 발주처는 없다

공공은 **11종을 도입**했다(챗봇·지식 검색·내규 조회·문서 요약·사전 검토·데이터 조회·
데이터 분석·안전관리계획·문서 인식·표준 보고서·회의록).
남은 2종은 화면이 '도입 전'으로 구분해 말한다

| 안 넣은 것 | 왜 |
|---|---|
| 문서 번역 | 한·영·일·중 4개 언어 대역 문장과 역번역 데이터가 필요하다. 부동산원 업무에서 성적서 번역은 핵심이 아니라 우선순위를 뒤로 뒀다 |
| 기준정보 표준화 | 주소 대장과 태그 매핑을 새로 써야 한다. 부동산원에는 **소재지 표준화**로 바꿔야 맞는데, 그건 옮기는 게 아니라 새로 설계하는 일이다 |

둘 다 **눌리지 않게 막아 두고 이유를 표시한다.** 억지로 열어 두면 제조 데이터가 나온다 — 카탈로그의 '준비 중'(아직 안 만든 화면)과 **다른 축**이다.
둘을 뭉뚱그리면 '없는 기능'과 '아직 안 산 기능'을 구분할 수 없다.

복합 업무 카드도 같은 이유로 공공에는 없다. 릴레이가 부르는 에이전트가 도입 전이라
띄워 두면 눌러도 아무 일 없는 버튼이 된다.

### 두 번째 팩이 드러낸 것

한 발주처만 있을 때는 안 보이던 것들이다.

| 발견 | 무엇이 문제였나 |
|---|---|
| 앱이 마운트 시 발주처 데이터를 불렀다 | 그때는 아직 어느 발주처인지 모른다. 팩이 하나뿐이라 안 드러났을 뿐 |
| 지식 검색 화면이 fixture를 직접 읽었다 | 예시 질의·견주는 사양이 발주처를 바꿔도 제조 것으로 남는다 |
| `simulateSearch`가 코퍼스를 기본값으로 썼다 | 기본값을 두면 발주처를 바꿔도 제조 도면이 걸린다 |
| 화면 테스트 100건이 '데이터 없음'으로 바뀌었다 | 페이지를 단독으로 그리면 발주처가 없다 — 경계가 의도대로 동작한다는 증거 |

### 옵션 이름까지 발주처 것이어야 한다 (2차)

에이전트를 3종 더 열면서(사전 검토·데이터 조회) 드러난 것이다.
**옵션 목록이 entities에 제조 콘텐츠로 박혀 있었다.**

| 자리 | 무엇이 박혀 있었나 |
|---|---|
| 사전 검토 | 규정 묶음 라벨 — `품질경영매뉴얼`은 제조 전용이다 |
| 데이터 조회 | 소스 라벨(`설비 대장`·`자재 재고`·`생산 실적`)과 예시 질의 |
| 사전 검토 훅 | 기본 선택이 `['labor','purchase']`로 박혀 있었다 — 그 코드가 없는 발주처는 아무것도 안 켜진 채로 열린다 |

코드 유니온(`'equipment' | …`)도 걷어냈다. 발주처마다 다른 것을 타입으로 못박으면
두 번째 발주처에서 반드시 어긋난다 — 서버도 테넌트별로 다른 목록을 준다.
지금은 **목록도 이름도 팩이 준다**(`GET /queries/sources`·`GET /reviews/regulation-sets`).

### 검사로 지킨다

- `src/fixtures/packs.test.ts` — `ready`인 발주처는 팩이 반드시 있고,
  **한 팩에 다른 발주처의 말이 한 글자도 없다**
- `e2e/tenant.spec.ts` — 발주처를 바꾸면 문서 목록이 실제로 바뀌고,
  화면 본문에 상대 발주처의 말이 안 나온다. 색도 실제로 바뀐다

공공 팩에 제조 문서를 섞어 넣어 실제로 실패하는지 확인했다.

## 4-5. 세 번째 발주처 — 팩이 반복 가능한가 (2026-08-05)

두 번째 팩(공공)까지는 만들 때마다 **코어를 고쳐야 했다.** 옵션 라벨이 entities에
박혀 있었고, 시뮬레이터가 데이터를 안에 물고 있었고, 화면이 fixture를 직접 읽었다.

세 번째(행정·한성시청)는 그걸 확인하는 시험이었다.

### 결과 — 코어를 한 줄도 안 고쳤다

한성시청 팩은 **값만 채워서 끝났다.** 새로 만든 것은 `src/fixtures/civic/` 6개 파일과
팩 조립 파일 하나뿐이고, `entities`·`shared/api`·`features`·`pages`는 손대지 않았다.
바꾼 코어 파일은 등록 두 줄(`packs.ts`)과 상태 한 줄(`domains.ts`)이다.

두 번째 팩에서 걷어낸 것들이 값을 했다.

| 두 번째 팩에서 걷어낸 것 | 세 번째 팩에서 |
|---|---|
| 규정 묶음 라벨(`품질경영매뉴얼`) | 팩이 준다 — 민원사무 처리지침·옥외광고물 조례… |
| 데이터 소스 라벨·예시 질의 | 팩이 준다 — 민원 처리 대장·옥외광고물 점검… |
| OCR·보고서·회의록 시뮬레이터 | 공장 함수에 값만 넣었다 |
| 예시 입력(참석자·안건) | 팩이 준다 |
| 지식 검색 예시·견주는 사양 | 팩이 준다 |

### 한성시청 팩

세계관은 **호우 대비 점검과 옥외광고물 정비**다. 축은 기한 도과 118건,
안전 기준 미달 광고물 25건, 강변동 민원 집중.

지도는 **인구 1천 명당 민원 접수**로 잰다 — 절대 건수로 재면 인구 많은 동이 늘
1위라 아무것도 알려 주지 않는다. 값이 없는 동 둘을 둔 이유도 같다
(행정동 통합·접수 창구 통합) — 0건이 아니라 집계가 없는 것이다.

도입 11종. 번역과 기준정보 표준화는 공공과 같은 이유로 도입 전이다.

### 검사

`packs.test.ts`의 마커에 행정을 더했고, `tenant.spec.ts`에 **세 발주처가 서로 다른
색·문서·에이전트를 쓰는지**와 **행정 화면에 앞선 두 발주처의 말이 없는지**를 넣었다.
행정 팩에 공공 문서를 섞어 실제로 실패하는지 확인했다.

## 4-6. 네 번째 발주처 — 다 채우자 검사가 흔들렸다 (2026-08-05)

의료(새빛대학교병원)를 채워 **포털의 '준비 중'이 0이 됐다.** 세 번째와 마찬가지로
코어는 등록 두 줄과 상태 한 줄만 고쳤고 나머지는 값이다.

세계관은 **삭감 위험 사전점검과 응급의료센터 과밀**이다. 축은 청구 보류 342건 중
회신 대기 18건, 응급 가동률 92.1%. 지도는 진료과별 병상 가동률로 재고, 값이
없는 진료과 둘(재활의학과·주간진료센터)을 남겨 뒀다 — 0이 아니라 안 재는 것이다.

⚠️ 이 팩은 환자를 다룬다. 문구는 **행정·심사 관점**으로만 썼고, 인식 예시의
개인정보도 직원 연락처로 뒀다. 환자 정보를 예시로 만들면 그 자체가 이 제품이
없애려는 것이 된다.

도입 11종. 번역과 기준정보 표준화는 앞선 팩과 같은 이유로 도입 전이다.

### 이번 팩이 드러낸 것 — 앞의 세 번은 안 보이던 두 가지

**① 업무 용어는 발주처 사이에 공유된다.** 누수 마커에 '청구'와 '이의신청'을
넣었더니 곧바로 오탐이 났다 — '청구'는 제조의 여비 정산에, '이의신청'은 공시와
심사 양쪽에 있다. 마커는 그 발주처에서만 쓰는 **좁은 말**로 골라야 한다.
넓게 잡은 검사는 '늑대야'를 외치고, 그러면 사람이 검사를 끈다.

**② 관리자 fixture가 포털의 진실을 복제하고 있었다.** `DOMAIN_EXPOSURE`와
관리자 팩 목록이 손으로 적은 값이라, 포털이 네 발주처를 여는데 관리자는
"업무 데이터 없음 3곳"이라고 말하고 있었다. 두 화면이 같은 것을 각자 적으면
반드시 갈라진다 — 둘 다 팩 레지스트리(`packStatuses()`)에서 **유도**하도록 고쳤다.

**③ 다 채우면 '빈 상태' 테스트가 밟을 데이터가 사라진다.** 포털의 '준비 중
발주처' 단언과 관리자의 '못 고르는 이유' 단언이 그래서 깨졌다. 지운 게 아니라
옮겼다 — 단위 테스트는 준비 중 발주처를 **주입해서** 그 경로를 계속 밟고,
E2E는 하드코딩된 숫자 대신 **포털이 여는 수와 관리자가 세는 수가 같은지**를 본다.

### 검사

마커에 의료를 더했고, `tenant.spec.ts`가 네 발주처의 색·문서·에이전트 결과와
서로의 말이 섞이지 않는지를 본다. 의료 팩에 공공의 말('표준지')을 넣어
실제로 실패하는 것을 확인하고 되돌렸다.

### 라이브에서 하나 더 나왔다 — 카탈로그가 제조의 말로 쓰여 있었다

배포본으로 네 발주처를 돌려 보다 **병원 허브에 `수출 문서 번역`이 떠 있는 것**을
봤다. 도입 전이라 못 누르지만 이름 자체가 제조의 말이다. 설명도 마찬가지였다 —
`설비 태그`, `공정 데이터`, `축적 도면`, `실적·재고`.

팩 데이터는 검사가 지키고 있었는데 **13종의 이름·설명은 코어에 박혀 있어
아무도 안 보고 있었다.** 업종 말을 걷어내고(`문서 번역`, `업무 데이터를…`)
카탈로그 전용 검사(`entities/agent/model.test.ts`)를 만들었다. 이름을 되돌려
실제로 실패하는 것을 확인했다.

**안 한 것:** 발주처마다 이름을 바꿔 부르게 하는 것(팩이 이름을 덮어쓰기).
허브 카드 이름과 화면 제목이 두 곳에 생겨 갈라진다 — 이 저장소가 여섯 번 겪은
실수다. 하려면 화면 제목까지 한 곳에서 나오게 고친 뒤에 한다.

**그리고 이것은 검사가 아니라 눈이 찾았다.** 화면을 실제로 켜 보는 일을
검사가 대신해 주지 않는다.

## 4-7. 에이전트 정의를 팩으로 (2026-08-05)

카탈로그를 고치고 다시 보니 **한 층 아래에 같은 문제가 있었다.** 병원 허브의
'데이터 조회' 카드는 2단계가 `MES 조회`, '데이터 분석'은 `센서 이력 결합`,
'안전관리계획 수립'은 `설비 상태 조회`였다. 담당도 전부 생산기술팀·설비보전팀.

카드에 뜨는 **단계 이름은 그 발주처의 업무 용어**이고 담당도 그 발주처 부서다 —
발주처 데이터인데 코어(`fixtures/agentdef.ts`)에 하나만 있었다.

### 옮긴 것

`DomainPackData`에 `agentDefs`·`scenarioDefs`를 넣고 팩 세 곳을 채웠다(제조는
기본 팩이라 fixtures 루트에 그대로 둔다). 도입한 11종만 정의를 갖는다 —
도입 전이면 정의도 없고, 카드가 단계를 안 그린다.

### 관리자는 발주처 소속이 아니다 — 이 변경이 드러낸 것

경계 함수를 발주처 인자로 바꾸자 **관리자 화면이 컴파일되지 않았다.** 관리자는
포털에서 들어올 때 발주처를 비우기 때문이다(`setActiveDomain(null)`).

숨기지 않고 화면에 올렸다 — 태스크플로우 빌더와 시나리오 빌더에 **발주처 선택**을
두고, 고른 발주처를 경계 함수에 넘긴다(`withPackOf`). 서버가 붙으면 그 값이
`X-Domain-Id` 헤더가 된다. 대신 새 질문이 생겨 제안서에 적었다(§3-2-1) —
**운영 담당자 토큰이 남의 발주처 정의를 읽어도 되는가.**

### 관리자와 포털이 같은 말을 하게

공공·행정·의료 팩에는 **도입하지 않은 에이전트를 부르는 시나리오**를 넣었다.
포털에 릴레이 카드가 없는 이유가 정확히 그것이기 때문이다. 시나리오 빌더는
이제 세 가지를 본다 — 카탈로그에 없는 에이전트 / **이 발주처가 안 산 에이전트** /
끊긴 도구. 가운데가 새로 생긴 판정이고, 그게 포털의 '카드 없음'과 같은 사실이다.

### 숫자가 발주처마다 갈린다

의료 팩만 실행형(안전관리계획)에 확인 지점을 걸어 두었다. 그래서 태스크플로우
빌더의 '사람 확인 없이 실행되는 에이전트'가 제조·공공·행정은 1종, 의료는 0종이다.
**0일 때도 화면이 말하게 했다** — 안 보여 주면 '없다'와 '안 쟀다'를 구분할 수 없다.

### 검사로 지킨다

- 팩 검사: 정의의 에이전트가 **도입 목록과 정확히 짝**인가(도입 전인데 정의가 있거나,
  도입했는데 정의가 없으면 실패)
- 누수 마커에 `MES`·`생산기술팀`·`설비보전팀` 추가
- 관리자 단위 테스트: 발주처를 바꾸면 단계와 판정이 **실제로 바뀌는가**
- E2E: 병원 허브에 제조의 단계가 **한 글자도** 없는가

의료 팩에 제조 정의를 다시 꽂아 **세 검사가 모두 실패하는 것**을 확인하고 되돌렸다.

### 남은 한계 → §4-8에서 닫았다

도구 목록이 아직 플랫폼 전역이라 `MES 조회`·`PdM 센서 조회`가 관리자 도구·배포와
대화 화면 오른쪽 패널에 남아 있었다. 다음 배치에서 옮겼다.

## 4-8. 도구도 발주처 것으로 (2026-08-05)

정의를 옮기고 나니 **도구가 남아 있었다.** 어느 발주처를 골라도 `MES 조회`·
`PdM 센서 조회`가 관리자 도구·배포 화면과 대화 화면 오른쪽 '연동 도구'에 떴다.
공장은 MES를 부르고 시청은 처리 대장을 부른다 — 도구도 발주처 데이터다.

`tools`·`mcpServers`를 팩에 넣고 도구·배포 화면에 발주처 선택을 달았다.
**배포는 안 갈랐다** — 플랫폼이 한 번 올리면 모든 발주처가 그 버전을 쓴다.
그래서 같은 화면 안에서 도구·서버 탭에만 발주처 선택이 붙는다.

### 옮기다 찾은 결함 — 사용처가 실제와 어긋나 있었다

도구마다 '이 도구를 쓰는 에이전트'를 **손으로 적어 두고** 있었다. 옮기려고 보니
`지식 검색`의 사용처에 안전관리계획이 없었다 — 그 에이전트의 2단계가 지식 검색을
부르는데도. 화면은 '끊기면 멈추는 에이전트'를 **실제보다 적게** 말하고 있었다.

목록을 고치지 않고 **유도하도록** 바꿨다. 팩은 도구만 갖고(`ToolSpec`), 사용처는
경계 함수가 정의에서 뽑는다(`ToolEntry`). 어긋날 자리가 없어진다.

### 발주처마다 다른 사실이 화면에 드러난다

| | 끊긴 도구 | 사외로 나가는 서버 |
|---|---|---|
| 한빛정밀 | PdM 센서 조회 → 데이터 분석·안전관리계획이 멈춘다 | ERP 연동(외부 위탁) |
| 한국부동산원 | 없음 | 실거래 신고 연계(기관 간) |
| 한성시청 | 강우 관측 연계 → 데이터 분석이 옛 값으로 답한다 | 관측소 연계(기관 간, 끊김) |
| 새빛대학교병원 | 없음 | 없음 — 진료 정보라 원내에서만 돈다 |

'없음'도 화면이 말하게 했다. 안 보여 주면 **끊긴 게 없는 것과 안 본 것**을
구분할 수 없다. 한성시청의 끊긴 도구는 호우 대비가 이 팩의 세계관인데 하필 그
판단에 쓰는 자료가 멈춰 있는 것이라, 이 제품이 드러내려는 위험 그 자체다.

### 검사로 지킨다

- 정의가 부르는 도구 id가 **그 팩의 도구에 있는가**(없으면 화면이 날 id를 그린다)
- 서버가 주는 도구 id도 같은 팩에 있는가
- 발주처를 바꾸면 도구 목록과 '못 도는 에이전트' 수가 실제로 바뀌는가(단위·E2E)
- 대화 화면의 연동 도구 패널도 발주처 것인가(E2E)

한성시청 도구 id를 하나 어긋나게 만들어 **두 검사가 실패하는 것**을 확인하고 되돌렸다.

## 4-9. 지식 영역과 나머지 2종 (2026-08-05)

### 지식 영역도 팩으로 — 포털이 전부 팩에서 나온다

도구를 옮기고 배포본을 보다 또 찾았다. 병원 대화 화면의 '답변 근거 > 지식 영역'에
`작업표준·공정 문서`·`설비 대장·정비 이력`·`협력사 공유 문서`가 떠 있었다.

`knowledgeAreas`·`indexEntries`·`agentOps`를 팩으로 옮기고, 관리자 지식 관리와
에이전트 화면에 발주처 선택을 달았다. **RAG 설정(임베딩 모델·청크 크기)은 안 갈랐다** —
플랫폼 선택이고, 화면이 그 사실을 함께 말한다.

운영 실적의 `areaIds`가 그 팩의 영역을 가리켜야 '기대는 영역에 못 찾는 문서가 있다'는
판정이 성립한다. 안 맞으면 판정이 조용히 빈 값이 되고 화면은 '빈틈 없음'이라는
**틀린 안심**을 준다 — 그래서 짝 맞춤을 검사로 지킨다.

**전수로 확인했다.** 포털 화면·위젯이 부르는 경계 함수 중 팩을 안 거치는 것은
`fetchDomain(s)`와 `setActiveDomain`뿐이다 — 발주처 레지스트리와 테넌시 설정
자체라 설계대로다. 이제 포털 **데이터**는 전부 팩에서 나온다.

### 그 확인이 놓친 것 — 하드코딩된 문자열

경계 함수만 훑고 "포털이 전부 팩에서 나온다"고 적었는데, 배포본을 다시 열어 보니
병원 화면에 그대로 있었다.

| 어디 | 무엇 |
|---|---|
| 챗봇 화면 안내 | `사내 규정·작업표준을 근거로 답변합니다` |
| FAQ 범주 칩 | `작업표준` (`entities/chat/model.ts`) |
| 회의록 첨부 목록 | `프레스_작업표준서_SOP-PR-011.pdf` (`useMeeting.ts`에 박힌 3건) |
| 지식 검색 입력창 | `예) 브래킷 굽힘 금형` |
| 사용 가이드 | `사내 규정·작업표준을 근거와 함께` |

**하드코딩된 문자열은 경계를 안 지난다.** 그래서 경계만 보는 확인으로는 절대
안 잡힌다. 범주 라벨과 안내 문구는 중립어로 바꾸고, 회의록 첨부와 지식 검색
예시는 팩에서 오게 했다.

그리고 같은 실수를 다시 못 하도록 **소스를 직접 읽는 검사**를 만들었다
(`scripts/core-vocabulary.test.ts`) — `entities`·`features`·`pages`·`widgets`에
한 업종의 말이 있으면 실패한다. 만들자마자 두 건을 더 찾았다.

만들면서 이 저장소가 이미 두 번 겪은 함정을 또 밟았다. `MES`가 `THEMES`에 걸려
오탐이 났다 — **마커는 낱말 경계로 봐야 한다.** 주석은 검사에서 뺐다. 사고 사례를
적어 둔 곳이라 업종 말이 그대로 들어 있고, 화면에 안 나가는 글자를 잡으면
검사가 '늑대야'를 외치게 된다.

릴레이(`useOrchestration.ts`)는 예외 목록에 적어 뒀다. 제조 이야기 하나로
고정돼 있고 다른 발주처에는 카드를 안 그리므로 화면에 나가지는 않는다 —
**예외를 검사 파일에 적어 두는 것 자체가 기록이다.**

### 나머지 2종 — 번역과 기준정보 표준화

세 발주처가 도입 전으로 남겨 뒀던 둘을 채웠다. 둘 다 계산은 코어에 두고
**말뭉치·대장만 팩이 주는** 공장 함수로 바꿨다(`makeTranslationSimulator`,
`makeAddressResolver`).

| | 번역 대상 | 표준화 대상 |
|---|---|---|
| 한빛정밀 | 검사성적서 | 설비 태그 + 사업장·협력사 주소 |
| 한국부동산원 | 외국인 대상 공시제도 안내문 | 필지 소재지 |
| 한성시청 | 외국인 주민 안내문(민원·호우) | 옥외광고물 위치 |
| 새빛대학교병원 | 외국인 환자 이용 안내문 | 청구 항목 코드 |

번역은 **역번역이 흔들리는 자리**를 발주처마다 다르게 뒀다. 공시는 제도 용어
(이의신청·과세표준), 행정은 처분 용어(계고·과태료), 의료는 비용 용어(본인부담금)다 —
전부 **나라마다 대응어가 없어서** 직역하면 뜻이나 강도가 바뀌는 말이다.
안내문에서 그게 어긋나면 사람이 기한을 놓치거나 비용을 잘못 이해한다.

**병원은 주소를 안 푼다.** 그래서 주소 관련 처리 유형을 아예 안 그린다 —
안 쓰는 유형을 라디오에 두면 고를 수 있는데 아무 일도 안 하는 칸이 된다.
처리 유형 목록·예시·대상 문서도 팩이 준다(`GET /mapping/config`).

### 다 채우자 또 테스트가 깨졌다 (세 번째)

네 발주처가 13종을 모두 도입하면서 '도입 전' 표시를 밟을 데이터가 없어졌다.
E2E는 지금 사실(전부 열려 있다)을 보게 바꾸고, **표시 경로는 단위 테스트가
도입 목록을 주입해** 계속 밟는다. 시나리오 빌더의 '안 산 에이전트' 판정도
같은 방식으로 순수 함수 테스트로 옮겼다.

### 남은 한계 → §4-10에서 닫았다

복합 업무 릴레이가 제조 이야기로 고정돼 있어 나머지 세 발주처는 허브에 카드를
그리지 않았다. 다음 배치에서 발주처별로 만들었다.

## 4-10. 릴레이도 발주처 것으로 (2026-08-05)

릴레이의 **구조**는 발주처와 무관하다 — 인식 → 표준화 → 조회 → 보고.
발주처마다 다른 것은 **부르는 값과 단계 이름**이다. 그래서 구조만 코어에 남기고
나머지를 팩(`relay`)으로 옮겼다.

| | 무엇이 들어오면 | 2단계 | 나오는 것 |
|---|---|---|---|
| 한빛정밀 | 검사성적서 스캔본 | 공급업체 주소 표준화 | 이상 발생 보고 초안 |
| 한국부동산원 | 이의신청서 스캔본 | 소재지 표준화 | 이의신청 검토 보고 초안 |
| 한성시청 | 옥외광고물 신고서 스캔본 | 표시 위치 표준화 | 신고 처리 공문 초안 |
| 새빛대학교병원 | 진료과 회신 서식 | **항목 코드 표준화** | 사전점검 보고 초안 |

**병원은 2단계가 아예 다르다.** 주소가 아니라 청구 항목 코드를 푼다 — 릴레이
구조는 같아도 부르는 처리 유형이 다르다. 그래서 2단계 결과 해석도 두 갈래를
모두 다룬다(주소 후보 판정 / 태그·코드 매핑 사유).

### 제목을 두 곳에 안 적는다

허브 카드 제목과 릴레이 화면 제목이 같아야 한다. 팩에 둘 다 적어 두면 언젠가
갈라지므로, 팩의 `scenario`는 **한 줄 소개만** 갖고 제목은
`relay.scenario.title`에서 온다. 경계 함수가 합쳐서 준다.

### 검사로 지킨다

- 소개(`scenario`)와 실행 설정(`relay`)이 **짝**인가 — 소개만 있으면 눌러도
  아무 일 없는 버튼이 된다
- 릴레이가 부르는 문서·조회 소스·처리 유형·에이전트가 **그 팩에 있는가** —
  없으면 중간에 실패하고, 사용자는 눌러 봐야 안다
- 병원 릴레이가 완주하고 제조의 말(`성적서`·`공급업체`·`설비 이력`)이 없는가(E2E)

의료 팩에 제조 릴레이를 꽂아 E2E가 실패하는 것을 확인하고 되돌렸다.
그리고 코어 어휘 검사의 **예외 목록이 비었다** — 릴레이가 유일한 예외였다.

## 4-11. 접근성 훑기 (2026-08-05)

규칙 엔진(axe)을 새로 깔지 않고 **자주 깨지는 것만 DOM에서 직접 봤다**
(`e2e/a11y-scan.spec.ts`) — 이름 없는 조작 요소, `h1` 개수, 제목 단계 건너뛰기,
끊긴 `aria-*` 참조, 명암비, 모바일 터치 타깃. 라이트·다크 양쪽을 본다.

### 앞의 다섯은 깨끗했다

이름·제목·`aria` 참조는 전 화면에서 결함 0건이었다. 이 저장소의 E2E가 처음부터
역할(`getByRole`)로 요소를 찾아 왔기 때문이다 — 이름이 없으면 테스트가 못 찾으니
자연히 붙었다. **검사 방식이 만든 결과**지 운이 아니다.

### 명암비는 깨져 있었다

흐린 글자 두 단계가 작은 글씨 기준(4.5:1)을 못 넘고 있었다.

| | 흰 바탕에서 | 무엇이 그 색이었나 |
|---|---|---|
| `text-slate-400` | **2.63:1** | 빈 상태 문구, 메뉴 그룹 라벨, 마지막 색인 시각, 저장 안내 |
| `text-slate-500` | **4.35:1** | 탭 라벨, 지표 단위, 부서명 |

전부 **읽어야 하는 글자**다. 화면마다 클래스를 바꾸지 않고 팔레트에서 한 번
낮췄다 — 다크 스킨을 변수 한 벌로 처리한 것과 같은 이유다. 두 단계의 차이는
남겼다. 하나로 합치면 '덜 중요한 것'과 '보조 정보'를 화면이 구분할 수 없다.

**다크에서 같은 자리가 다시 깨졌다.** 팔레트를 반대편 색조로 뒤집는 규칙이라
라이트에서 낮춘 값이 다크에서는 배경에 가까워졌다(2.35:1). 다크의 두 단계만
규칙의 예외로 두고 밝기를 올렸다 — **한쪽만 재고 끝냈으면 못 봤을 결함이다.**

포털의 '관리자 시스템' 버튼만 브라우저 기본 포커스 테두리를 쓰고 있던 것도
발주처 카드와 같은 표시로 맞췄다.

### 검사를 만들면서 밟은 함정 셋

- **덜 그려진 화면을 훑었다.** 처음 결과가 '결함 0건'이었는데, `goto` 직후라
  화면에 버튼이 하나뿐이었다. 훑은 조작 요소 수를 세어 **너무 적으면 실패**하게
  고쳤다 — 이 저장소가 이미 겪은 '통과한 것과 본 것은 다르다'의 재판이다.
- **색을 문자열로 파싱했다.** 요즘 계산값은 `oklch()`로 온다. `rgb()`만 읽는
  정규식이라 배경을 못 찾고 전부 흰색으로 쳐서 오탐이 쏟아졌다. 캔버스에 1픽셀
  칠하고 그 픽셀을 읽는 방식으로 바꿨다(`fillStyle`을 되읽는 방법은 안 된다 —
  브라우저가 `oklch`를 그대로 돌려준다).
- **전환 중인 색을 쟀다.** 탭 애니메이션 중간값이 명암비 위반으로 잡혔다.
  재는 동안 전환을 끈다.

숨긴 파일 입력(1×1)은 터치 타깃에서 뺐다 — 누르는 것은 그 앞의 라벨이다.

## 4-12. 규칙 엔진과 낭독기 재료 (2026-08-05)

### axe를 들였다 — 직접 만든 훑기가 못 본 것을 잡으라고

직접 만든 훑기는 **내가 고른 항목만** 본다. 규칙 엔진은 내가 생각 못 한 것을 본다.
둘 다 남겼다 — 우리 화면의 규칙(발주처 전환·다크 팔레트)은 앞쪽이 알고,
일반 규칙은 엔진이 안다.

**의존성을 넣는 것 자체가 이 저장소에서 두 번 CI를 깬 일**이라 절차를 지켰다.
Windows에서 `npm i`를 돌리자 예상대로 리눅스용 항목 3개(`@emnapi/*`)가 잠금
파일에서 사라졌다. HEAD의 잠금 파일을 기준으로 **추가된 2개만 병합**하고
`npm ci`로 확인했다 — 최종 차이는 삽입 25줄, 삭제 0줄이다.

엔진이 잡은 것:

| 위반 | 무엇이었나 |
|---|---|
| `scrollable-region-focusable` | 가로 스크롤 표 31곳에 **키보드로 닿을 수 없었다.** 마우스 휠·손가락으로만 볼 수 있는 표였다 |
| `color-contrast` 2건 | 오탐이었다 — 탭 전환 애니메이션 중간값 |

스크롤 표는 전부 `tabIndex={0}`을 붙여 키보드로 스크롤되게 했다. 오탐은 엔진
쪽에서도 전환을 끄고 재도록 고쳤다 — **직접 만든 훑기에서 이미 밟은 함정을
엔진 쪽에서 한 번 더 밟았다.**

그 오탐을 파다 알게 된 사실 하나: 흰 글자 대 발주처 브랜드 색이 의료(보라)에서
5.70:1로 **가장 아슬아슬하다.** 새 발주처가 밝은 색을 고르면 그 발주처만 글자가
안 보이는데, 화면을 열기 전에는 모른다. 그래서 색을 적는 자리에서 걸리도록
단위 검사를 붙였다(`fixtures/domains.test.ts`).

### 낭독기 — 확인한 것과 못 한 것

**확인한 것**: 낭독기가 읽는 재료인 접근성 트리를 그대로 꺼내 봤다
(`e2e/screenreader.spec.ts`). 본문 랜드마크가 하나인가, 이름이 겹치는 버튼이
없는가(겹치면 "버튼, 시작하기"를 열세 번 듣고도 못 고른다), 결과 영역에 이름이
있는가, 진행 중임을 알리는가.

여기서 결함을 하나 찾았다. **알림 자리가 상태가 바뀔 때 비로소 만들어지고 있었다** —
그렇게 하면 낭독기가 첫 변화를 놓치는 경우가 있다. 자리는 늘 두고 내용만 채우도록
고쳤다(에이전트 셸에 빈 `role="status"` 상주).

**못 한 것**: NVDA·VoiceOver를 실제로 돌리지 않았다. 낭독 순서·억양·중복 발화는
사람이 들어 봐야 안다. 이 검사가 통과했다고 "낭독기로 확인했다"고 말하면 안 된다 —
검사 파일 맨 위에도 그렇게 적어 두었다. → 사람이 따라 할 대본을 §4-14에 만들었다.

## 4-13. 접근성 게이트를 CI에서 갈라 보이게 (2026-08-05)

E2E가 한 덩어리라 CI가 빨개졌을 때 **접근성 때문인지 기능 때문인지 로그를 열어야**
알 수 있었다. 접근성 테스트에 `@a11y` 태그를 붙이고 CI를 두 step으로 갈랐다.

### 잡(job)이 아니라 step으로 나눈 이유 — 재 봤다

| | 테스트 수 | 소요 |
|---|---|---|
| 접근성(`@a11y`) | 20 | **10초** |
| 기능 | 274 | 58초 |

잡을 나누면 checkout·`npm ci`·build·preview·브라우저 설치가 한 번 더 돌아
**2~3분이 는다.** 10초를 병렬로 벌자고 3분을 더 쓰는 셈이라 step으로 나눴다.
목적(빨간 이유를 화면에서 바로 알기)은 step 이름으로 그대로 달성된다.

### 구멍이 안 나게

두 명령은 **같은 태그의 여집합**이다(`--grep @a11y` / `--grep-invert @a11y`).
그래서 어떤 테스트도 양쪽에서 다 빠질 수 없고, 태그를 안 붙인 새 테스트는
기능 쪽으로 간다 — 안 도는 게 아니라.

그래도 누군가 `--grep`을 다른 태그로 바꾸면 그 순간 조용히 빠지는 테스트가
생긴다. **두 몫의 합이 전체와 같은지를 CI가 먼저 센다**(20 + 274 = 294).
이 저장소가 '이름 검사가 조용히 통과'에서 배운 것을 그대로 적용했다.

### 이 안을 적대적으로 검증했더니 내 구현에서 결함 셋이 나왔다

설계와 별개로 **반박 전용 검토**를 붙였다. 세 가지가 나왔고 전부 맞았다.

- **`if: always()`가 없었다.** 기능 step이 깨지면 접근성은 아예 안 돈다 —
  그 커밋의 접근성은 통과도 실패도 아닌 **'안 봄'**인데, 화면에는 빨간 verify
  하나만 남아 안 본 것이 안 보인다. 이 저장소가 가장 싫어하는 상태를 내가 만들었다.
- **포트가 남는다.** `reuseExistingServer`는 CI에서 false이고 `--strictPort`다.
  실패한 실행이 preview를 남기면 다음 step이 '포트 사용 중'으로 죽는데,
  `if: always()`가 하필 그 직후에 접근성을 돌린다. 접근성 결과 대신 포트 오류가
  뜨면 목적이 정면으로 깨진다 — 정리 step을 앞에 뒀다.
- **주석이 거짓이었다.** `verify가 만든 dist를 그대로 배포한다`고 적혀 있었지만,
  playwright의 webServer가 CI에서 다시 빌드해 덮어쓴다. 분리 전부터 사실이 아니었다.
  주석을 사실대로 고쳤다.

덤으로 **`e2e/`가 어느 tsconfig 프로젝트에도 없었다**는 것도 드러났다.
`npm run typecheck`가 스펙을 한 번도 검사한 적이 없어서, 스펙의 타입 오류는
E2E를 돌려야만 드러났다 — 그러면 '접근성 step이 빨간 것 = 접근성 위반'이라는
말이 성립하지 않는다. `tsconfig.e2e.json`을 만들어 게이트가 먼저 잡게 했다
(스펙에 타입 오류를 넣어 실제로 걸리는 것을 확인했다).

### 부수 — 잠금 파일을 저장소 절차대로 다시 만들었다

axe를 넣을 때 잠금 파일을 손으로 병합했다. 저장소에는 이미 리눅스에서 다시
만드는 워크플로(`lockfile.yml`)가 있었으므로 그걸 돌려 받아 **손으로 만든 것과
대조**했다 — 패키지 419개가 정확히 일치했고 차이는 `peer` 표시 29건뿐이었다.
그래도 정본은 리눅스 생성본으로 바꿨다. 손으로 맞춘 것이 맞았더라도,
**도구가 만든 것을 쓰는 편이 다음 사람에게 안전하다.**

## 4-14. 낭독기 대본 — 그리고 그걸 만들다 찾은 결함 15건 (2026-08-05)

사람이 NVDA로 직접 듣고 판정할 대본을 만들었다(`docs/A11Y-SCREENREADER.md`).
흐름 7개, 매번 확인 12개. **자동 검사가 이미 보는 것은 뺐다** — 여기 있는 것은
기계가 판정할 수 없는 것뿐이다.

### 대본을 만들려고 소스를 훑다가 결함이 쏟아졌다

대본을 쓰려면 "무엇이 들려야 하는가"를 알아야 하고, 그걸 알려면 소스를 읽어야
한다. 읽는 동안 **자동 검사 세 겹이 전부 통과시킨 결함 15건**이 나왔다.
치명 3 · 높음 8 · 보통 4. 전부 파일·행과 실측값이 붙어 있다.

가장 무거운 셋:

| 무엇 | 왜 자동으로 못 잡나 |
|---|---|
| 챗봇 **답변이 도착한 것을 아무도 말하지 않는다** | axe의 69개 규칙 중 라이브 리전 관련이 0개다. 리전 부재는 규칙 위반이 아니라 설계 누락이라 판정 대상 밖이다 |
| 릴레이가 **'확인 지점 N건'을 말하지 않는다** | '진행 중 → 완료' 전이를 알리는지는 규칙화 대상이 아니다 |
| 화면이 바뀌는데 **포커스가 body로 떨어진다** | 우리 키보드 테스트가 Tab 흔적을 찍기만 하고 **어디로 갔는지는 판정하지 않았다** |

'AI가 못 한 것을 드러낸다'는 이 제품의 원칙이 **화면에만 있고 소리에는 없다**는
것이 셋의 공통점이다.

### 검증이 대본 자체의 오류도 잡았다

대본을 그대로 실행하면 못 따라가는 지점이 있었다 — 존재하지 않는 문구 인용
1건('사람 확인 2곳'은 실제로 1곳), 도달 불가능한 단계 1건, 포커스 예측이 틀려
**더 나쁜 실패를 정상으로 적게 만드는** 자리 4곳. 반박 검토가 소스와 하나씩
대조해 찾았다. 대본은 사람이 그대로 따라가는 물건이라, 틀린 대본은 없는 것보다 나쁘다.

### 그 과정에서 콘텐츠 누수 셋이 더 나왔다

지도·라이브 지표 카드를 훑다 발견했다 — 이 저장소가 이번 세션 내내 잡아 온
바로 그 종류다.

- 지도 제목이 병원인데 **`사업장별 병상 가동률`** (`사업장`이 코어에 박혀 있었다)
- 가동률 92.1%가 임계 90을 **넘었는데** 배지는 `기준 미달` — 뜻이 정반대다
- 응급실 지표 초과 문구가 **`운전을 계속하지 말고 보전 진단을 받으십시오`**

`siteLabel`·`overAdvice`를 팩으로 옮기고, 임계 배지는 지표 방향(`lowerIsWorse`)에
따라 '미달/초과'가 뒤집히게 했다. 코어 어휘 검사에 `사업장`·`보전 진단`을 더했더니
`entities/packops/model.ts`의 `사업장 지표`가 하나 더 걸렸다.

### 검사에 넣은 '조용한 무시' 하나를 없앴다

axe의 관리자 순회가 메뉴를 못 찾으면 `continue`로 넘기고 있었다. 못 찾은 것을
모아 실패시키게 고쳤더니 **곧바로 걸렸다** — `시나리오 빌더`는 '에이전트'의 하위
메뉴라 부모를 연 직후에만 보이는데 순서가 맨 뒤였고, 모바일에서는 메뉴가
오버레이라 한 번 고르면 닫혀서 **셋을 조용히 건너뛰고 있었다.** 순서를 고치고
매번 다시 열게 했다. 그 전까지 이 검사는 초록불이었다.

## 4-15. 결함 15건을 전부 고쳤다 (2026-08-06)

§4-14가 찾아 놓은 15건을 닫았다. 자동 검사 26개 → **38개**.

### 고친 것과 '어디에 두느냐'의 규칙

| # | 무엇 | 어디에 |
|---|---|---|
| 1·2·6 | 도착·완료를 말하지 않는다 | 상주 `role="status"` 하나를 두고, **보이는 쪽을 `aria-hidden`으로 내린다** |
| 3·13 | 화면이 바뀌어도 알 길이 없다 | `features/screen-change/useScreenChange.ts` — 제목·알림·포커스 셋을 함께 |
| 4 | 오버레이가 모달이 아니다 | `features/overlay/useModalOverlay.ts` — dialog·트랩·Esc·복귀·`inert`·넓히면 닫기 |
| 5·9·10·11 | 이름이 겹치거나 어긋난다 | 보이는 글자를 이름 앞에(WCAG 2.5.3), 역할은 덮어쓰지 않는 자리에 |
| 7 | 표에 행 머리글이 없다 | 27화면 29행을 `<th scope="row">`로 |
| 12 | 기준을 넘는 순간에 말이 없다 | 이미 있던 경고 문장 **자체**를 `role="alert"`로 |
| 14 | 한국어가 `lang="en"` 아래 | 원문 그대로 두는 자리에 `lang="ko"`, 환경설정만 되돌림 |
| 15 | 건너뛰기가 없다 | `shared/ui/SkipLink.tsx`를 두 셸의 첫 정지점에 |

한 줄로 반복된 규칙이 있다. **같은 말을 화면과 소리 두 군데에 두지 않는다.**
라이브 리전을 새로 만들면 보이는 쪽을 내리고, 보이는 문장으로 충분하면 그 문장에
역할을 붙인다(12번이 그 경우다 — 문장이 상태가 뒤집힐 때만 바뀌므로 전이 순간에만 말한다).

### 검사가 '판정을 포기한 것'과 '통과'를 갈랐다

이번 15건 중 셋은 **세 검사가 모두 초록불인 채로** 있던 것이다.

- `bypass`는 skip link·랜드마크·제목 중 하나라도 있으면 통과다 → `<main>`이 있으니
  건너뛰기 0건이어도 pass. 그래서 규칙이 아니라 **횟수**를 세는 검사를 새로 썼다.
- 대화상자 규칙은 `role="dialog"`가 **있을 때만** 돈다 → 역할을 안 붙이면 대상 밖.
  그래서 규칙 대신 **동작**(포커스 진입·트랩·Esc·복귀·배경 `inert`)을 본다.
- `lang="en"`은 문법적으로 유효한 값이라 언어 규칙 넷이 전부 통과한다 → 글자가 실제로
  무슨 언어인지는 axe가 판단하지 않는다. 그래서 **한글이 든 요소마다 가장 가까운
  `lang`**을 직접 본다.

셋 다 '검사가 없다'가 아니라 '검사가 있는데 판정을 포기했다'였다. 통과 목록에 섞이면
구별되지 않는다 — §4-13에서 얻은 교훈(초록불의 뜻을 확인하라)이 그대로 반복됐다.

### 고치다 만든 결함 셋 — 전부 실행해서 잡았다

- **표 머리글 일괄 변환이 한 화면을 깨뜨렸다.** 데이터 조회 결과표는 칸을 반복해서
  그린다(`columns.map`). '`<tr>` 뒤 첫 `<td>`'라는 규칙을 그대로 적용하면 **모든 칸**이
  행 머리글이 되고, className이 템플릿 리터럴이라 `className`이 두 번 붙은 잘못된 JSX가
  나왔다. 자리(`ci === 0`)를 보도록 손으로 고쳤다. 기계 치환은 27화면 중 26곳에서 맞았고
  **한 곳에서 틀렸다** — 전수 스캔(중복 속성·셀 반복 표)이 그 한 곳을 짚었다.
- **화면 전환 훅과 건너뛰기 링크가 부딪쳤다.** 훅이 포커스를 이미 `<main>`으로 옮겨
  두므로 Tab을 눌러도 건너뛰기에 닿지 않는다. 동작은 옳다(이미 본문에 있다). 검사 쪽을
  고쳤다 — 문서 맨 위에서 시작하는 사람을 재현해야 한다. `blur()`만으로는 안 됐다:
  크로미움은 '다음 Tab이 시작할 자리'를 blur 뒤에도 들고 있어서, `body`에 포커스를
  줘야 자리가 옮겨진다.
- **`lang` 검사가 내가 만든 알림을 잡았다.** 화면 전환 알림이 번역된 탭 이름을 한국어
  문장에 끼워 「Chat 화면입니다」가 됐다. 다른 가지(에이전트명·관리자 메뉴)는 전부
  한국어 원문이라, 통째로 한국어로 통일했다. 반씩 섞인 문장은 어느 음성으로도 제대로
  안 읽힌다.

### 잃을 뻔한 것 — `prettier --write`

작업 도중 `npx prettier --write "src/**/*.tsx"`를 돌렸다. **이 저장소는 prettier를
쓰지 않는다**(설정 파일도 의존성도 없다 — `npx`가 그때 내려받았다). 손으로 맞춘 형식이
121파일에서 통째로 뒤집혔고, 그 안에 되돌리면 안 되는 편집이 섞여 있었다.

되돌린 방법: `git archive HEAD`로 원본 트리를 꺼내 **같은 prettier를 먹인 사본**을 만들고,
파일마다 그 사본과 현재 파일을 비교했다. 같으면 형식만 바뀐 것이므로 HEAD로 복원(79개),
다르면 의미 있는 편집이 든 것이다(36개). 그중 26개는 표 머리글 변환뿐이라 저장소 형식으로
다시 돌렸고, 나머지 10개만 손으로 옮겼다. **검증은 반대 방향으로** 했다 — 복원한 결과에
다시 prettier를 먹여 백업과 대조해 29/36이 완전 일치, 나머지 7은 주석 줄바꿈과 import
묶음 차이뿐임을 확인했다. 이 대조가 아니었다면 표 변환이 깨뜨린 데이터 조회 화면도
그대로 남았을 것이다.

교훈: **형식 도구는 저장소가 그걸 쓸 때만 쓴다.** 설정 파일이 없다는 것은 '기본값으로
쓰라'가 아니라 '쓰지 않는다'는 뜻이다.

## 5. 재구축 중에 잡은 결함

이전 데모에서 넘어온 것이 아니라 **다시 만드는 과정에서 생겼다가 잡힌 것**들이다.
같은 실수를 반복하지 않기 위해 남긴다.

| 결함 | 어떻게 드러났나 |
|---|---|
| 한글 경로에서 `vite build`가 조용히 죽음 | 모듈 30개는 통과, 2,357개에서 크래시. ASCII 경로에서 같은 코드가 통과해 원인 확정 |
| CI `npm ci` 실패 | Windows에서 만든 lockfile에 Linux용 항목이 빠짐. CI 환경에서 lockfile을 만들어 해결(D-008) |
| E2E가 남의 dev 서버를 테스트 | 포트 5173이 흔해서. 5180 고정 + strictPort |
| 차트 E2E가 두 번째에만 통과 | dev 서버가 요청 시점에 컴파일. CI는 preview 빌드로 전환(D-007) |
| 사이드바 중복 렌더로 라벨 끊김 | 같은 `id`가 DOM에 둘 생겨 모바일 워크스페이스 선택이 이름 없는 콤보박스가 됨. E2E가 잡음 |
| 무른 단언 | 검색 방식 테스트가 요약 문구를 비교하고 있었다. 방식 이름·소요 시간은 결과가 같아도 달라진다 |
| 라이브 지표가 1배속에서 안 움직임 | 관측 간격을 10분으로 잡아 전체 재생에 90분이 걸렸다. E2E가 60배속에서도 안 끝나는 것으로 드러났다. 1분 간격으로 줄여 1배속에서도 변화가 보이게 했다 |
| 렌더 중 `Date.now()` | `useRef(Date.now())`가 렌더마다 다른 시작 시각을 만들 수 있었다. ESLint 순수성 규칙이 잡았고, 기준점을 effect에서 잡도록 고쳤다 |
| 사전으로 옮기며 문구가 어긋남 | 사이드바 여는 버튼을 '사이드바 펼치기'로 새로 썼는데 기존 이름은 '사이드바 열기'였다. 모바일 진입점 20곳이 한꺼번에 막혔다. E2E 전체가 잡았다 — 문구를 옮길 때는 새로 쓰지 말고 그대로 옮긴다 |
| 지도 타일 색이 다크에서 안 보임 | 타일 배경을 고정 `rgba()`로 칠해 팔레트를 안 따라갔다. 변수를 섞도록(`color-mix`) 바꿨다 |
| 새 경계 함수 6개가 제안서에 빠짐 | 관리자 API를 만들고 문서를 안 고쳤다. **계약 드리프트 테스트가 잡았다** — 이 테스트를 만든 이유가 이것이다 |
| 정렬 테스트가 무름 | 가장 오래 기다린 승인 신청이 fixture 맨 앞에 있어, 정렬을 지워도 테스트가 통과했다. **탐지 확인이 잡았다.** fixture를 접수순으로 바꿔 정렬이 일을 하게 만들었다 |
| 진행하면 깨지는 테스트 | 관리 홈의 '준비 중 카드' 단언이 화면을 하나 만들 때마다 깨졌다. 하드코딩 대신 카드 목록에서 준비 중 개수를 **유도**하도록 고쳤다 |
| 같은 종류가 E2E에도 | '준비 중 메뉴' E2E가 특정 메뉴를 지목해 그 화면을 만들 때마다 깨졌다(세 번째). 배지가 붙은 것을 찾아 누르도록 바꿔 무엇이 남았든 동작하게 했다 |
| 조사를 괄호로 얼버무림 | '업무 문서이(가) 없어'가 라이브에 그대로 나갔다. 이름이 데이터에서 오므로 문장에 박아 둘 수 없어 받침으로 고르는 함수(`shared/lib/korean.ts`)를 만들었다. **한 배치 뒤 시나리오 빌더에서 같은 실수를 반복**했고 또 라이브에서 잡았다 — 함수를 만들어 둔 것과 쓰는 것은 다르다. `이(가)`·`을(를)`·`은(는)` 전수 검색으로 남은 곳이 없는지 확인했다 |
| **로컬 게이트가 CI보다 좁았다** | 로컬에서 `tsc -p tsconfig.app.json`만 돌리고 CI는 `tsc -b`(전체)로 돈다. 테스트 tsconfig에서만 걸리는 타입 오류가 로컬을 통과해 CI에서 처음 터졌다. 게이트는 CI와 같은 명령(`npm run typecheck`)으로 돌린다 |
| 메뉴 이름과 화면 제목이 다름 | 같은 것을 두 번 쓰면 갈라진다. **여섯 번 갈라졌다** — 접근권한·차단 / HR 연계 / 데이터셋 / 평가 결과 / API·프롬프트 / AI 품질 관리. 전수 검사(`e2e/naming.spec.ts`)를 만들었고 만들자마자 다섯 번째를 찾았다 |
| **관리자가 포털과 다른 말을 함** | 네 번째 발주처를 열었는데 관리자는 "업무 데이터 없음 3곳"이라고 했다. 손으로 적은 fixture가 포털의 진실을 복제하고 있었다. 둘 다 팩 레지스트리에서 유도하도록 고쳤고, **두 화면의 수가 같은지**를 E2E가 본다 |
| 다 채우니 빈 상태 테스트가 깨짐 | '준비 중 발주처'·'못 고르는 이유'를 밟을 데이터가 사라졌다. 단언을 지우는 대신 단위 테스트가 준비 중 발주처를 **주입**해 그 렌더 경로를 계속 밟게 했다 |
| **검사가 조용히 통과** | 그 이름 검사가 하위 메뉴를 못 찾으면 `continue`로 넘어가고 있었다 — 통과했지만 하위 20여 개를 안 본 상태였다. 여섯 번째 갈라짐을 전수 순회가 눈으로 찾아 드러났다. 못 찾은 것이 있으면 그 자체로 실패하도록 고쳤다. **통과한 것과 본 것은 다르다** |

### 검증 방식 — 탐지 확인

테스트를 쓴 뒤 **결함을 일부러 다시 넣어 실제로 실패하는지 확인**한다.
통과만 보면 단언이 무른지 알 수 없다. 이 습관으로 위 '무른 단언'을 찾았다.
